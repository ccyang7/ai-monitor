# 模块五：异常分析

> 对应开发阶段：**阶段 9（监控数据分析）**。

------

## 1. 模块目标

用**简单规则**识别项目中的异常调用，让用户不用自己盯着数据看。

V1 不需要复杂的 AI Evaluation，只要能回答：

```text
有没有异常的调用？
有哪些调用失败了？
```

------

## 2. 异常判定基准

"正常"必须有明确的定义才能实现，否则代码无法下笔。

**V1 采用滑动基线：**

```text
基线 = 该模型近 7 天的平均 Token / 平均响应时间

Token 异常    ：本次 total_tokens > 基线 × 5
响应时间异常  ：本次 latency     > 基线 × 5
```

### 约束

| 约束 | 原因 |
|---|---|
| 倍数阈值（默认 5）通过**配置项**控制 | 便于调整，不重新部署 |
| **按模型分别计算基线** | 不同模型的正常水位差异很大（reasoner 天然比 chat 慢且长） |
| 样本不足时（近 7 天该模型调用 < 10 次）不做判定 | 避免数据少时误报 |

> V1 **不使用**统计学方法（分位数、标准差、时间序列预测）。规则越简单越容易解释和调试。

------

## 3. 三类异常

### 3.1 Token 异常

```text
近 7 天平均：  2,000 Token
本次调用：    25,000 Token
```

系统标记：

> ⚠️ Token 使用异常

### 3.2 响应时间异常

```text
近 7 天平均：  2s
本次调用：    15s
```

标记：

> ⚠️ 响应时间异常

### 3.3 调用失败

以下失败类型统一记录：

```text
API Error
Timeout
Rate Limit
```

失败来自上报数据的 `status = "error"`，错误详情在 `error_message` 字段。

### 3.4 成本异常（可选）

同一类规则可以复用到成本：

```text
本次 estimated_cost > 该模型近 7 天平均成本 × 5
```

这只是 Token 异常的另一种呈现 —— 成本由 Token 推导，两者通常同时触发。**V1 可以只做 Token 和响应时间两类。**

------

## 4. 异常数据展示

异常**只针对当前项目**（同模块三、四的隔离要求）。

### 4.1 概览页提醒

```text
AI网站生成平台

需要注意

⚠️ 最近出现 3 次高 Token 请求
⚠️ 今天出现 2 次 API 超时
```

### 4.2 异常日志列表

点击提醒后进入异常列表，展示：

```text
时间
模型
异常类型（高 Token / 慢响应 / 失败）
关键指标（实际的 Token / 耗时 / 错误信息）
```

------

## 5. 实现方式

两种可选路线，**V1 推荐方案 A**：

| | 方案 A：查询时计算 | 方案 B：写入时标记 |
|---|---|---|
| 做法 | 查日志时实时对比基线，动态判定 | 上报时立即判定，把 `is_anomaly` 存进表 |
| 优点 | 阈值改了，历史判定跟着更新；实现简单 | 查询快 |
| 缺点 | 查询时多一次基线计算 | 阈值改了，历史标记不会更新；表结构多字段 |

> 方案 A 的问题是每次查询都要算基线 —— 但基线可以按"模型 + 日期"缓存（这也正好是阶段 8 引入 Redis 的一个合理用途）。

### 5.1 基线查询示意

```sql
-- 某模型近 7 天的平均 Token
SELECT AVG(total_tokens)
FROM llm_request
WHERE project_id = :project_id
  AND model = :model
  AND created_at >= NOW() - INTERVAL '7 days'
```
