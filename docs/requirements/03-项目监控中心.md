# 模块三：项目监控中心

> 对应开发阶段：**阶段 7（Token / Cost 统计）、阶段 9（监控数据分析）**。

------

## 1. 模块目标

用户点击某个项目后进入的页面，是**整个系统的核心页面**。

它回答四个问题：

```text
今天调用了多少次？
消耗了多少 Token？
花了多少钱？
平均响应多长时间？
有没有异常？
```

------

## 2. 概览

### 2.1 核心指标

进入项目后首先展示该项目的：

```text
今日调用次数
今日 Token
今日费用
平均响应时间
```

所有这些数据**只属于当前项目**。

### 2.2 最近调用

展示当前项目最近的调用：

```text
11:42
生成奶茶店官网
18,293 Token
2.8s
成功
```

### 2.3 异常提醒

如果项目存在异常，在概览页顶部显示：

```text
需要注意

⚠️ 最近出现 3 次高 Token 请求
⚠️ 今天出现 2 次 API Timeout
```

点击后进入异常日志列表（见模块五）。

## 3. Token 分析

### 3.1 时间范围

```text
今日
近7天
近30天
自定义时间
```

### 3.2 统计项

```text
调用次数
输入 Token
输出 Token

```

### 3.3 趋势

按天展示 Token 使用趋势。

**重点不是展示复杂图表，而是帮助用户回答：**

> ⚠️ 不要因为用了 ECharts 就把页面变成"图表墙"（见模块九 UI 原则）。

## 4. 成本分析

### 4.1 统计项

```text
今日费用
近7天费用
近30天费用
```

并给出简单结论（先结论后数据）：

```text
本项目近7天预计费用

¥8.62

相比上周：
↑ 32%

主要原因：
单次请求 Token 增加
```

### 4.2 成本计算公式

```text
estimated_cost = input_tokens  / 1_000_000 × input_price
               + output_tokens / 1_000_000 × output_price
```

### 4.3 计算时机：写入时快照（V1 采用）

日志写入时，按**当时**的模型价格算好 `estimated_cost` 存入 `LLMRequest` 表。

| | 优点 | 代价 |
|---|---|---|
| 写入时快照 ✅ | 历史成本不可变；统计时直接求和，无需 join 价格表 | 价格修正后无法追溯重算历史成本 |

> **为什么选快照**：成本类数据"历史不可变"更符合用户心智 —— 用户不希望改一次价格，上周的账单跟着变。

> **说明**：Token 用量来自模型返回的 usage 字段，本身可能存在偏差，因此平台展示的成本始终是"**预计**费用"。

## 6. 数据来源与查询要点

所有指标都来自对 `llm_request` 表的聚合查询。

### 6.1 必须建立的索引

```text
llm_request(project_id, created_at)
```

这是本模块所有查询的基础。**建表时就要建**，成本几乎为零，收益极大。

### 6.2 查询模式

```sql
-- 今日指标（示意）
SELECT COUNT(*), SUM(total_tokens), SUM(estimated_cost), AVG(latency)
FROM llm_request
WHERE project_id = :project_id
  AND created_at >= :today_start
  AND created_at <  :tomorrow_start
```

### 6.3 ⚠️ 每个查询都必须带 project_id

本模块的每个接口都属于"隔离区" —— 数据绝不能跨项目。

后端通过 `Depends(get_own_project)` 拿到 `project` 对象后，查询语句中**必须**带上 `project_id` 过滤。

## 8. Redis 缓存（阶段 8）

阶段 8 会引入 Redis。**必须明确缓存对象和失效时机**，否则它是负资产。

建议的缓存对象：

```text
项目概览的今日指标     → 缓存 60 秒（高频访问、短时间不要求精确）
```

不建议缓存的：

```text
日志列表（筛选条件组合太多，命中率低）
趋势数据（本身查询成本不高）
```

> 原则：**先确认有性能问题，再上缓存**。缓存带来的失效策略和数据一致性问题是真实的开发成本。
