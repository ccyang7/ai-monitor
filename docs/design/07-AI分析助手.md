# 设计文档 07：AI 分析助手

> 对应需求：[07-AI分析助手](../requirements/07-AI分析助手.md)
> 对应阶段：**阶段 11（工具与 Agent）、阶段 12（会话与流式）**

这是整个项目**技术上最复杂**的模块，也是需求文档里约束写得最多的模块（18.2 / 18.3 / 21.2）。

------

## 1. 形态：全局助手，不是项目助手

| | 项目助手（已放弃） | **全局助手（V1 采纳）** |
|---|---|---|
| 入口 | 项目内的页面 | 任意页面（含首页） |
| 上下文 | 固定某个项目 | 无固定项目 |
| 能问 | "这个项目今天用量多少" | "今天各个项目的使用情况"、"A 和 B 的用量对比" |
| 权限边界 | `project_id` | **`user_id`** |

### 1.1 ⚠️ 权限边界上移是理解本模块的关键

项目助手的权限边界是"当前项目"，全局助手没有这个边界了。那靠什么保证不串数据？

**答案：靠登录态里的 `user_id`。**

```text
模型能影响的：工具调用的参数（比如 project_name = "B项目"）
模型不能影响的：current_user_id（来自 JWT，服务端注入）
```

> 这解决了需求讨论阶段最大的争议 —— "AI 工具的权限不能交给 AI 判断"。
>
> 现在边界是登录态，模型再怎么被诱导，也只能在**当前用户自己的项目**范围内查询。
> 它可以把 `project_name` 传成任意值，但服务端会校验这个名字属不属于当前用户。

## 2. 硬约束与软约束

### 2.1 硬约束（代码保证，提示词影响不了）

| 编号 | 约束 | 实现位置 |
|---|---|---|
| H1 | 用户只能查到自己的数据 | 工具函数内部过滤 `user_id` |
| H2 | 工具参数里的项目名必须属于当前用户 | 工具内部查 `owner_id` |
| H3 | 项目名解析不到 → 返回错误信息，不猜 | 工具内部 |
| H4 | 用户不能通过助手写入 / 删除任何数据 | **不提供任何写工具** |

### 2.2 软约束（提示词建议，模型可以不听）

- 回答尽量简洁
- 数字要带单位
- 查不到数据时如实说明，不要编造

> **为什么要区分**：软约束就算模型不遵守，最坏结果是"回答啰嗦"或"格式不好看"，
> 不会造成安全事故。硬约束必须由代码保证，**因为它们一旦失效就是数据泄露**。
>
> 这个划分方式本身就是一种设计能力：**先问"这条规则失效的最坏后果是什么"，再决定放在哪一层。**

### 2.3 ⚠️ H3 值得单独说

```text
用户问：「A项目用量怎么样」
模型调用：get_usage_stats(project_name="A项目", ...)
服务端：当前用户名下不存在「A项目」
       ↓
返回给模型：{"error": "项目「A项目」不存在。当前用户的项目有：AI知识问答、代码助手"}
       ↓
模型：如实告诉用户
```

**为什么返回错误信息而不是抛异常**：抛异常会中断整个 Agent 流程；返回结构化的错误信息，模型能继续推理（比如提示用户"你是不是想问 XX 项目"）。

> 但错误信息里**只能包含当前用户自己的项目名** —— 不能返回"系统中存在叫这个名的项目，但不是你的"，
> 那又是一次信息泄露。**错误信息也要过隔离。**

## 3. 工具设计

### 3.1 工具清单

| 工具 | 参数（模型填写） | 内部注入 | 返回 |
|---|---|---|---|
| `list_projects` | —— | user_id | 项目列表 |
| `get_project_overview` | project_name | user_id | 概览指标 |
| `get_usage_stats` | project_name, start_date, end_date | user_id | 汇总 + 趋势 |
| `compare_projects` | project_names[] | user_id | 各项目对比数据 |
| `get_recent_logs` | project_name, limit | user_id | 日志摘要 |
| `get_error_logs` | project_name, limit | user_id | 错误日志 |
| `analyze_anomalies` | project_name | user_id | 异常列表 |
| `list_models` | —— | —— | 可用模型（内置 + 自建） |

### 3.2 ⚠️ 工具签名里绝对没有 user_id

```python
@tool
def get_usage_stats(project_name: str, start_date: str, end_date: str) -> dict:
    """查询指定项目在时间范围内的 Token 用量和成本统计。

    Args:
        project_name: 项目名称（用户口中的名字，不是 ID）
        start_date: 开始日期，格式 YYYY-MM-DD
        end_date: 结束日期，格式 YYYY-MM-DD
    """
```

`user_id` 不在这里 —— 它由服务端在执行工具时注入（见 §4.2）。

> **这是整个模块最重要的设计**：模型看到的工具签名里根本没有 `user_id` 这个参数，
> 所以它**连尝试越权的机会都没有**（不是"不能传"，是"没这个参数可传"）。
>
> 从"校验模型传的 user_id 对不对"变成"模型根本传不了 user_id" —— 后者是结构性安全。

### 3.3 为什么用项目名而不是 project_id

用户说话是"A项目怎么样"，不是"项目 3 怎么样"。让模型去查 id 需要多一轮工具调用。

**服务端负责把名字解析成 id**，顺带完成归属校验：

```text
project_name → WHERE name = :name AND owner_id = :current_user_id
             → 找到：返回
             → 找不到：返回错误信息（见 §2.3）
```

> 一次查询同时完成"解析"和"鉴权" —— **没有单独一步叫"校验权限"，权限校验融在数据查询里**。
> 这是最不容易遗漏的形式。

### 3.4 工具的 docstring 就是给模型的说明

LangChain 的 `@tool` 装饰器用 **docstring 作为工具描述**。所以：

```text
✅ 写清楚这个工具能回答什么问题
✅ 参数说明写清楚格式和含义
❌ 不要写"TODO"或空着
```

> 工具描述的质量直接决定模型选对工具的概率 —— 这相当于在写"给 AI 看的 API 文档"。

## 4. 实现方案（LangChain）

### 4.1 Agent 构建

用 LangChain 的 `create_agent`（不是旧版的 `AgentExecutor`）：

```text
model = init_chat_model(
    model=..., model_provider="openai",
    base_url=..., api_key=...,        # OpenAI 兼容端点
)
agent = create_agent(model, tools=[...], system_prompt=...)
```

> 底层是 LangGraph。**不要照抄网上早期教程的 `initialize_agent` / `AgentExecutor`** —— 那些 API 已过时。

### 4.2 ⚠️ user_id 怎么注入（本模块的核心技术点）

工具函数本身不能接收 `user_id` 参数（否则模型会看到它），但内部需要用。

**方案：用 `contextvars` + 请求上下文**

```text
① 接口层：从 JWT 拿到 current_user_id
② 存入一个请求级的 context 变量
③ 工具函数内部读取这个变量
④ 请求结束，变量自动清理
```

> 关键在于：**`user_id` 从"参数"变成了"环境"**。
> 参数是模型控制的，环境是服务端控制的。这就是 §3.2 说的"结构性安全"的落地方式。

**替代方案**：用 LangChain 的工具调用时的 `config` 参数传递（LangGraph 支持在运行时传 config）。
两种都可行，选一种，**关键是不要在工具签名里暴露 user_id**。

### 4.3 工具执行流程

```text
模型决定调用 get_usage_stats(project_name="A项目", ...)
   ↓
LangGraph 执行工具函数
   ↓
工具内部：读取 context 里的 user_id
   ↓
调 services/stats.py 的查询函数（复用 03 模块的代码）
   ↓
返回结果给模型
   ↓
模型继续推理 / 给最终答案
```

> **工具函数是"薄封装"** —— 真正的查询逻辑在 `services/` 里，工具只做"参数适配 + 上下文注入"。
> 这样同一个查询既能被 HTTP 接口调用，也能被 AI 工具调用，逻辑只有一份。

## 5. 会话管理

用 LangGraph 的 `checkpointer` + `thread_id`：

```text
每个会话一个 thread_id
   ↓
checkpointer 保存消息历史
   ↓
下一次同 thread_id 的调用自动带上历史
```

### 5.1 ⚠️ thread_id 必须与用户绑定

如果 thread_id 可以被猜到，A 用户构造一个 B 用户的 thread_id，就可能读到别人的对话历史。

**做法**：`thread_id = f"user_{current_user_id}_{会话编号}"` 或者存表并校验归属。

> **这是本项目里最容易被忽略的一个越权点** —— 所有注意力都在"数据查询"上，
> 忘了"对话历史"本身也是需要隔离的数据。

### 5.2 checkpointer 的选择

| 类型 | 适用 |
|---|---|
| `MemorySaver` | 开发期，重启即丢 |
| Redis / PostgreSQL checkpointer | 生产 |

**V1 可以先用 MemorySaver**（阶段 11-12 先跑通），但要在文档里标注这是临时方案。

> 开发期先跑通，生产前替换 —— 这是合理的分阶段策略，**前提是知道自己在偷懒**。

## 6. API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/chat` | 发消息（非流式，方便调试） |
| POST | `/api/v1/chat/stream` | 发消息（SSE 流式，前端用） |
| GET | `/api/v1/chat/sessions` | 会话列表 |

### 6.1 请求

```json
{
  "message": "今天各个项目的使用情况如何？",
  "thread_id": "可选，不传则新建会话"
}
```

### 6.2 响应

```json
{
  "thread_id": "user_1_a3f2",
  "reply": "今天三个项目共调用 145 次，消耗 82 万 Token...",
  "tool_calls": [
    {"tool": "list_projects", "args": {}},
    {"tool": "get_usage_stats", "args": {"project_name": "AI知识问答", "start_date": "2026-10-08", "end_date": "2026-10-09"}}
  ]
}
```

> **返回 `tool_calls` 是很有用的调试信息** —— 出问题时你能立刻看出是"模型没调工具"还是"工具查错了"。
> 前端可以不展示（或放在折叠区里）。

### 6.3 流式输出

SSE（Server-Sent Events）。FastAPI 用 `StreamingResponse`。

> **为什么用 SSE 不用 WebSocket**：单向推送（服务端 → 前端），SSE 更简单，且能走普通 HTTP。

## 7. 边界情况

| 情况 | 处理 |
|---|---|
| 用户问和监控无关的问题 | 提示词引导它说明能力范围（软约束，不强制） |
| 用户问的项目不存在 | 工具返回错误信息，模型如实转述 |
| 用户问的项目不属于自己 | 同上（且错误信息里**不能透露存在性**） |
| 模型陷入工具调用循环 | 设最大轮次上限（如 10 轮） |
| LLM 服务不可用 | 返回 503 + 友好提示 |
| 用户反复发消息 | 频率限制（V1 可不做，记录为已知风险） |
| 查询返回大量数据 | 工具内部限制条数（如日志最多 20 条）后返回 |
| 对话历史过长 | 超出模型上下文时截断或摘要（V1 记录为已知限制） |

### 7.1 ⚠️ 最大轮次上限是必须的

模型可能反复调用工具而不给答案（尤其工具一直返回错误时）。

**V1 设 10 轮上限**，超过则中断并返回"分析超时，请换个问法"。

> 没有这个上限，一次坏请求可能消耗大量 Token 并长时间占用连接。

## 8. 实现顺序建议

```text
① ai/tools.py            先写工具函数（不接 LLM，直接用 Python 调用验证）
② 验证工具              手写参数调用，确认隔离生效（用两个用户交叉测）
③ ai/agent.py            接 LangChain，跑通单轮问答
④ 上下文注入             user_id 注入机制
⑤ api/chat.py            接口（先非流式）
⑥ 会话管理               checkpointer + thread_id
⑦ 流式输出               SSE
```

### 8.1 ⚠️ 第 ② 步不能省

**在接 LLM 之前，先手工构造两个用户的数据，直接调用工具函数，确认 A 用户拿不到 B 用户的数据。**

接上 LLM 之后，出问题时你分不清是"工具实现错了"还是"模型没调对工具"。先隔离变量。

> 这是调试复杂系统的通用策略：**分层验证，从底往上**。

## 9. 与其他模块的关系

| 关系 | 说明 |
|---|---|
| 强依赖 03（监控中心） | 工具内部调它的查询 |
| 强依赖 04（日志） | `get_recent_logs` / `get_error_logs` |
| 强依赖 05（异常分析） | `analyze_anomalies` |
| 强依赖 06（模型管理） | `list_models` |
| 依赖 01（用户与项目） | `list_projects` 用 owner_id 过滤 |

> **本模块是"集大成者"** —— 它不产生新数据，只是把前面所有模块的查询能力暴露给 LLM。
> 所以它**必须最后做**，且前面每个模块的隔离做好了，它才可能是安全的。
