------

## 1. 异常的四种类型

| 类型 | 判定信号 | 粒度 | 用户关心的问题 |
|---|---|---|---|
| `token` | `total_tokens` 远超基线 | 单条记录 | 是不是被刷了？哪里在烧 Token？ |
| `latency` | `latency` 远超基线 | 单条记录 | 模型服务是不是有问题？ |
| `error` | `status = 'error'` | 单条记录 | 具体是哪几次调用挂了？挂了什么错？ |
| `error_rate` | 时间窗口内 `error` 占比超阈值 | 时间窗口 | 接入是不是整体坏了？ |

> **为什么「失败」要拆成两个类型**：它们的答案不一样。`error` 回答「哪几次挂了」，
> 一次挂一次列，用户点进去能看 `error_message`；`error_rate` 回答「是不是整体不行了」，
> 偶尔挂一两次不用管，一天里挂掉三成才是事故。只做前者会被零星的失败刷屏，
> 只做后者又查不到具体是哪些调用挂了。

### 1.1 什么是「基线」

**基线 = 这个项目的这个模型，在最近 7 天里的正常水平。**

```text
基线 = AVG(total_tokens) 和 AVG(latency)
     范围：同一 project_id + 同一 model
     条件：created_at >= now() - 7 天
     且 status = 'success'（排除失败样本，它们的 latency 不具代表性）
```

> **为什么基线要按模型分开算**：`deepseek-chat` 和 `gpt-4` 的正常 Token 量差好几倍，
> 混在一起算会让"正常"变得毫无意义。
>
> **为什么基线要按项目分开算**：每个项目的业务不同 —— 一个做摘要、一个做代码生成，
> 正常的 Token 量根本不在一个量级。

## 2. 判定规则

### 2.1 阈值（可配置）

```text
TOKEN_ANOMALY_RATIO   = 5.0    单次 Token > 基线 5 倍
LATENCY_ANOMALY_RATIO = 3.0    单次延迟 > 基线 3 倍
ERROR_RATE_THRESHOLD  = 0.2    窗口内错误率 > 20%
BASELINE_MIN_SAMPLES  = 10     样本不足 10 条 → 不判定
```

### 2.2 ⚠️ `BASELINE_MIN_SAMPLES` 是最重要的一条

如果一个模型只有 2 条历史记录，算出"平均 1000 Token"，那么第 3 条 3000 Token 的调用就是"3 倍异常"。

**这是噪声，不是异常。** 样本太少时基线不可信，**必须放弃判定**，否则页面上会刷出一堆假异常，用户很快就会不再看它。

> 这体现一个通用原则：**宁可漏报，不可误报。**
> 告警类功能一旦开始误报，用户就会忽略它 —— 那么真正异常出现时也失效了。

### 2.3 阈值为什么可配置

不同项目对"异常"的容忍度不同。硬编码的 5 倍对某些场景太敏感，对另一些太迟钝。

V1 放在 `config.py` 里（全局一套），不做成用户可调 —— 后者需要加表、加界面，收益不匹配。

## 3. ⚠️ 核心设计决策：什么时候判定

三种方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 查询时计算 | 每次查异常列表时实时算 | 每次都要算基线 |
| B. 写入时标记 | 上报时判定，存 `is_anomaly` 字段 | **基线依赖历史，写入时算不准** |
| C. 定时任务扫描 | 后台任务定期跑 | 需要调度器，复杂度高 |

### 3.1 选 A（查询时计算）

**理由**：

1. 阈值改了立即生效 —— 不需要重算历史数据
2. 不用加字段 —— 表结构保持干净
3. 基线可以缓存 —— 性能问题有解

### 3.2 ⚠️ 为什么 B 不行（值得记住）

写入时标记看起来更"高效"（算一次存下来），但有个致命问题：

```text
判定一条记录是否异常，需要「它之前的 7 天基线」
       ↓
写入时能拿到基线 ✅
       ↓
但基线的定义可能变（阈值调整、样本范围调整）
       ↓
已经标记的记录怎么办？重算？那还不如查询时算
```

**结论**：凡是"判定标准可能变化"的场景，**存结论不如存事实**。
存储原始数据（Token、延迟），判定逻辑放在查询时。

> 这是数据建模的一个通用规律：**派生数据尽量不落库**，除非有明确的性能理由。

## 4. API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects/{project_id}/anomalies` | 异常列表 |

### 4.1 查询参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `start_date` | datetime | **必填** | 与 03/04 一致：区间左闭右开 |
| `end_date` | datetime | **必填** | |
| `type` | str | 不限 | `token` / `latency` / `error` / `error_rate` |
| `page` / `page_size` | int | 1 / 20 | `page_size` 上限 100 |
| `tz` | str | `UTC` | 只影响 `error_rate` 的窗口按哪一天切 |

> 起止时间是**必填**，没有「默认近 7 天」这一说。给默认值意味着前后端各有一份
> 「默认」的定义，用户换个页面再回来看到的数据范围可能就变了；必填则由前端明确决定
> 并把选择回显在界面上。跨度上限 3660 天，和统计接口共用同一套校验。

### 4.2 响应

```json
{
  "items": [
    {
      "type": "token",
      "created_at": "2026-10-06T11:42:31Z",
      "log_id": 1024,
      "model": "deepseek-chat",
      "value": 18293,
      "baseline": 2100,
      "ratio": 8.7,
      "window": null,
      "error_message": null
    },
    {
      "type": "error_rate",
      "created_at": "2026-10-06T00:00:00Z",
      "log_id": null,
      "model": null,
      "value": 0.3333,
      "baseline": 0.2,
      "ratio": 1.7,
      "window": "2026-10-06",
      "error_message": null
    }
  ],
  "total": 3,
  "page": 1,
  "page_size": 20,
  "baseline_available": true,
  "insufficient_baselines": [
    { "model": "qwen-max", "samples": 4, "required": 10 }
  ]
}
```

四类异常共用同一个 item，各自只填自己有的字段：

| 类型 | `log_id` | `window` | `value` | `baseline` | `ratio` | `error_message` |
|---|---|---|---|---|---|---|
| `token` / `latency` | 有 | —— | 实际值 | 基线均值 | 实际 / 基线 | —— |
| `error` | 有 | —— | —— | —— | —— | 有 |
| `error_rate` | —— | 日期 | 错误率 | 阈值 0.2 | 错误率 / 阈值 | —— |

> **`baseline` 字段在窗口类里装的是阈值而不是均值**：这样前端能用同一套
> 「实际值 vs 参考值」渲染四种类型，不必为 `error_rate` 单写一套。
>
> **`baseline_available` 只描述 `token` / `latency` 能不能判**：它取 false 时
> 列表未必是空的 —— `error` 和 `error_rate` 不依赖基线，项目刚接入照样能报出失败。
> 前端应该用它的措辞是「样本还不够，暂不做用量与延迟判定」，
> 而不是「没有异常」。
>
> ⚠️ **`insufficient_baselines` 是后来补的，因为一个布尔值说不出「哪里不够」**：
> 项目里三个模型，两个攒够了、一个才 4 次，此时 `baseline_available` 是 `true`，
> 界面看着一切正常，可那一路其实还没开始判定 —— 用户永远不会知道。
> 带上 `samples` 和 `required` 之后，提示就能写成「再积累 6 次调用后开始判定」，
> 而不是干巴巴的一句「样本不足」。
>
> 只列**样本不足**的模型。达标的不需要提示，全列出来等于让前端自己筛。
>
> `ratio` 由服务端算好返回 —— 前端不用再算一遍，也保证展示口径一致。

## 5. 实现流程

```text
① 校验 ownership（get_own_project）
② 查基线
      样本不足 → baseline_available = false，token / latency 两类不判
③ token / latency：查区间内的成功调用，逐条比对
④ error：查区间内的失败调用，逐条列出
⑤ error_rate：按天分组，算错误占比，超阈值产出一条窗口异常
⑥ 合并四类 → 按 type 过滤 → 按时间倒序 → 切片分页
```

四类判定各自一次查询，在 Python 里合并，没有拼成一条大 SQL。原因有两个：
四类的 WHERE 条件完全不同（成功 / 失败 / 分组），拼起来只会更难读；
分开之后「某类判定出 bug」的影响面就限定在那一个函数里。

### 5.1 基线查询

```sql
SELECT
  model,
  AVG(total_tokens) AS avg_tokens,
  AVG(latency)      AS avg_latency,
  COUNT(*)          AS samples
FROM llm_requests
WHERE project_id = :project_id
  AND status = 'success'
  AND created_at >= now() - interval '7 days'
GROUP BY model
```

> ⚠️ **实现修订：样本门槛从 SQL 的 `HAVING COUNT(*) >= 10` 挪到了 Python。**
> 反正要逐行看，顺手把 `COUNT(*)` 带出来，就能在同一个查询里拿到「样本不足的
> 模型各有几条」—— 界面因此能说出还差几次，而不是笼统地报一句「样本不足」。
> 代价是没达标的模型也进了结果集，一行一个模型，忽略不计。

### 5.2 基线缓存 —— 本期不做

设计时打算用 Redis 缓存基线（键 `baseline:{project_id}`，TTL 10 分钟）。**实现时省掉了。**

基线查询是一次带 `HAVING` 的分组聚合，走 `(project_id, created_at)` 索引，V1 的数据量下毫秒级返回。
为它引入 Redis 等于在没有任何慢查询证据的情况下增加一个部署依赖 —— 而 Redis 挂了还要决定
「用陈旧基线」还是「整个异常页报错」，白白多出一层故障模式。

真要加的时候，位置就在 `services/anomaly.py` 的 `_baselines()` 里，改一个函数，不动别处。

> 值得记的是当初支持缓存的那个理由 —— 「overview 要实时、基线不要求实时，缓存策略要跟着数据的性质走」。
> 这个判断本身没错，错的是在性能问题出现之前就把它实现了。

### 5.3 ⚠️ 判定范围要排除基线期

计算基线用的是"最近 7 天"，那判定范围**不能也是这 7 天** —— 否则异常样本会污染基线，把基线拉高，导致异常不再异常（自我稀释）。

```text
基线期：now() - 7 天  ~  now()
判定期：建议用更早的数据，或接受这个近似
```

**V1 的做法**：接受这个近似（影响很小），但要在代码注释里写清楚。

> 严格的统计学做法是"用 T-14 ~ T-7 的数据当基线，判定 T-7 ~ T 的数据"。
> V1 不值得为这个精度增加复杂度，但要知道这里有简化。

## 6. 边界情况

| 情况 | 处理 |
|---|---|
| 样本不足 10 条 | token / latency 不判定，`baseline_available = false`（error / error_rate 照常） |
| 基线平均值为 0（全是 0 Token） | 跳过该类判定（0 的任意倍还是 0，硬算就是除零） |
| 某模型只有失败记录 | 该模型无基线 → 不做用量与延迟判定 |
| 项目无任何数据 | 空列表 + `baseline_available = false` |
| 一次调用同时超两类阈值 | 产出两条异常，`log_id` 相同、`type` 不同 |

### 6.1 错误率异常的判定方式不同

前三种是**单条记录**判定（这条 Token 太多了 / 这次挂了），错误率是**时间窗口**判定：

```text
按天（或按小时）分组，窗口用 :tz 切：
  当天总调用 >= 10 条
  且 当天错误数 / 当天总调用 > 20%
      → 记为一条「错误率异常」
```

所以错误率异常的 `log_id` 为 null，改为返回 `window`（如 `"2026-10-06"`）。

**窗口的门槛复用了 `BASELINE_MIN_SAMPLES`** —— 两个参数要的其实是同一件事：
「多少条才算数」。3 次调用里错 1 次是 33%，可那什么都说明不了。

**窗口按 `:tz` 切分而不是固定 UTC**：一天是「用户的今天」还是「UTC 的今天」，
误差能有 8 小时。`created_at AT TIME ZONE :tz` 拿到的是当地墙钟值，
组装 `created_at` 时要先补回时区再转 UTC —— 直接 `replace(tzinfo=utc)` 会整体差一个时区。

> **响应模型要能容纳两种形态** —— 要么给 `log_id`，要么给 `window`。
> 这也说明一个接口里混了两种粒度时，schema 要设计得足够宽容。

## 7. 实现顺序

```text
① config.py              四个阈值配置项
② schemas/common.py      抽出 TimeRangeQuery（与统计接口共用的区间与时区校验）
③ schemas/anomaly.py     查询参数 + 响应模型
④ services/anomaly.py    基线计算 + 四类判定
⑤ api/anomaly.py         路由；main.py 注册
⑥ api/stats.py           overview 组装 anomaly_counts
⑦ scripts/check_anomaly.py  验收
```

### 7.1 ⚠️ 与统计模块的循环依赖

异常判定要复用统计模块的区间条件表达式和分桶表达式（都是 `AT TIME ZONE :tz` 那一套逻辑，
抄一份迟早会不一致）。于是 `services/anomaly.py` 单向 `import` 自 `services/stats.py` ——
两个内部函数因此去掉了下划线前缀，改名 `range_conditions` / `bucket_expr`。

**方向必须是单向的**，所以 `anomaly_counts` 不在 stats service 里算，而是在
`api/stats.py` 的路由层组装：

```text
api/stats.py ──→ services/stats.py
     └─────────→ services/anomaly.py ──→ services/stats.py   ← 只有这一条是有向的
```

> 放在 service 层「顺手算一下」很诱人，但那会让 stats 与 anomaly 互相 import。
> 路由层是唯一同时认识两边的地方，这段胶水放这里最合适。
> 项目小的时候靠自觉，项目大了靠分层 —— 这里是分层先立住的一个小例子。

### 7.2 验证方法

[02-数据接入](02-数据接入.md) 的播种脚本会**刻意生成少量异常样本**（超长 Token、超长延迟）。
验收脚本 `scripts/check_anomaly.py` 覆盖两个方向：

```text
✅ 植入的异常，全部被检出
✅ 正常数据，没有被误判为异常
```

**两个方向都要验** —— 只验"检出了异常"不够，还要验"没有误报"。

几点实现上的讲究：

- **判定期刻意排在基线窗口之外**（`NOW-14d ~ NOW-8d` 对基线 `NOW-7d ~ NOW`），
  两段不重叠，基线里不会混进被判定的样本，断言才能写死数字
- **正反成对**：Token 那条断言「超 5 倍检出」，同时断言「正好等于基线的不报」；
  延迟断言「4 倍检出」+「2.5 倍不报」；错误率断言「12 里错 4 报」+「12 里错 2 不报」
  +「5 里错 3 不报（样本不够）」
- 数据一律相对 `NOW` 生成，写死日期的话只要日期滑出 7 天，基线就永远是空的，
  测出来的「零误报」其实是「什么都没判」
