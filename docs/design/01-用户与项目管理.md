# 设计文档 01：用户与项目管理

> 对应阶段：**阶段 3**

## 1. 涉及的表

`users`、`projects`、`api_keys` —— 具体字段见[总设计 §4](README.md#4-数据库表结构全貌)。

### 1.1 本模块需要补充的约束

| 表 | 约束 |
|---|---|
| users | `username` 唯一、`email` 唯一 |
| projects | `owner_id` 索引；`name` 在同一用户下唯一 |
| api_keys | `key_hash` 唯一索引；`key_prefix` 仅用于展示 |

> **项目名在同一用户下唯一**是业务规则，需要在 service 层校验，不强制加数据库唯一索引
> （因为以后可能有软删除，数据库唯一约束会挡住重建同名项目的操作）。

## 2. API 接口

### 2.1 认证

| 方法 | 路径 | 说明 | 状态码 |
|---|---|---|---|
| POST | `/api/v1/auth/register` | 注册 | 201 |
| POST | `/api/v1/auth/login` | 登录，返回 access_token | 200 |
| GET | `/api/v1/users/me` | 当前用户信息（需登录） | 200 |

**登录响应**：

```json
{
  "access_token": "eyJhbGciOi...",
  "token_type": "bearer",
  "expires_in": 604800
}
```

**认证方式**：后续请求带 `Authorization: Bearer <token>`。

校验这个头用 FastAPI 的 `HTTPBearer`，**不用** `OAuth2PasswordBearer`：

> `OAuth2PasswordBearer` 是为 OAuth2 的 `password` 流程准备的，它要求登录接口接收
> `application/x-www-form-urlencoded` 表单（字段名固定为 `username`/`password`）。
> 而我们的登录接口收的是 JSON。用它就得把登录接口改成表单，或者做一个字段名
> 对不上的中间层 —— 为了一个我们用不到的 OAuth2 语义引入两处不必要的耦合。
>
> `HTTPBearer` 只做一件事：从 `Authorization` 头里取出 Bearer 令牌。这正是我们需要的。
> 代价是 `/docs` 页面上的「Authorize」按钮不会代填用户名密码（那个表单是 OAuth2 流程专用的），
> 需要手动粘贴 token —— V1 可接受。
>
> **JWT 的 `sub` 声明必须是字符串**。PyJWT 2.10 起在解码时强制校验这一点，
> 编码时传 int 不会报错、解码时才抛 `InvalidSubjectError`。所以签发时写
> `str(user_id)`，解析后自己转回 `int`。
>
> **V1 不做 refresh token** —— 直接用有效期 7 天的 access_token。
> 生产环境应该做 refresh 机制，但那会引入额外的表和续期逻辑，V1 不值得。

### 2.2 项目

| 方法 | 路径 | 说明 | 状态码 |
|---|---|---|---|
| GET | `/api/v1/projects` | 当前用户的项目列表 | 200 |
| POST | `/api/v1/projects` | 创建项目（返回项目 + 首个 API Key） | 201 |
| GET | `/api/v1/projects/{project_id}` | 项目详情 | 200 |
| PATCH | `/api/v1/projects/{project_id}` | 编辑项目（只改传过来的字段） | 200 |
| DELETE | `/api/v1/projects/{project_id}` | 删除项目 | 204 |

> **删除成功返回 204（No Content）而不是 200 + 一个 `{"ok": true}`**：204 语义上就是
> 「成功了，但没有响应体」。返回体是空的，前端 `fetch` 拿到 `response.status === 204`
> 直接处理即可，不需要再多一层「解析出来的东西长什么样」的判断。

**创建项目请求**：

```json
{
  "name": "AI知识问答",
  "description": "微信小程序端的知识问答应用",
  "tech_stack": "Python"
}
```

**创建项目响应**（201）：

```json
{
  "id": 1,
  "name": "AI知识问答",
  "description": "...",
  "tech_stack": "Python",
  "status": "active",
  "created_at": "2026-10-08T12:00:00Z",
  "api_key": "proj_a1b2c3d4e5f6..."
}
```

> ⚠️ **API Key 的明文只在此刻返回一次**。之后接口只返回 `key_prefix`。
> 这是标准做法（同 GitHub Token）：明文只出现一次，服务端只存哈希，丢了就重新生成。

**项目列表响应**（首页用）：

```json
{
  "items": [
    {
      "id": 1,
      "name": "AI知识问答",
      "tech_stack": "Python",
      "status": "active",
      "last_called_at": "2026-10-08T11:58:00Z",
      "has_anomaly": false
    }
  ],
  "total": 1
}
```

> `last_called_at` 和 `has_anomaly` 是**跨项目聚合**的结果（每个项目的最新日志时间），
> 属于"聚合区"—— 过滤维度是 `owner_id`，不是 `project_id`。

**编辑项目请求**（PATCH，三个字段都可选）：

```json
{
  "name": "AI知识问答 v2",
  "description": "换了模型重新压测过"
}
```

响应 200，返回**更新后的完整项目对象**，结构与 `GET /projects/{project_id}` 完全一致 ——
前端拿到就能直接替换本地状态，不需要再补一次详情请求。

> **为什么是 PATCH 而不是 PUT**：PUT 的语义是「用请求体整体替换这个资源」。前端
> 只想改个描述、却没把 `tech_stack` 发回来，它的值就会被静默清空 —— 这种误伤在
> 排查时几乎不会怀疑到接口设计上。PATCH 只改请求体里**出现过**的字段。
>
> **「没传」和「传了 null」必须能区分开**：`description` 不传 = 不动它，
> `description: null` = 清空它。在 Pydantic v2 里这两者在 `model_dump()` 的结果中
> 长得一模一样，必须用 `model_dump(exclude_unset=True)` 才分辨得出来。
> **这是本接口唯一容易写错的地方。**
>
> **改名查重要排除自己**（`WHERE id != project_id`）：否则用户打开编辑框、什么都不改
> 直接保存，就会撞上自己当前的名字，收到「同名项目已存在」。
>
> **`status` 不在可改字段里**：它是系统字段。V1 只有 `active` 一种取值，归档属于后续阶段。
>
> 越权校验走和 `GET` / `DELETE` 相同的 `get_own_project` 依赖 ——
> 这是本模块**第三个**越权入口。

### 2.3 API Key

| 方法 | 路径 | 说明 | 状态码 |
|---|---|---|---|
| GET | `/api/v1/projects/{project_id}/api-keys` | 列出（只返回 prefix，只列有效 Key） | 200 |
| POST | `/api/v1/projects/{project_id}/api-keys` | 新建（返回明文一次） | 201 |
| DELETE | `/api/v1/api-keys/{key_id}` | 吊销 | 204 |

**为什么支持多个 Key**：轮换时可以先加新 Key、切换、再吊销旧 Key，服务不中断。

**「吊销」是软操作，不是物理删除**：

```text
DELETE /api/v1/api-keys/{key_id}
   → UPDATE api_keys SET status = 'revoked' WHERE id = ?
   （记录仍在表里）
```

不物理删除的两个理由：

1. **阶段 4 的数据接入接口要靠这个状态**。接入方拿着已吊销的 Key 来上报数据时，
   服务端必须能查到这个哈希、发现 `status = 'revoked'`、然后返回 401。
   如果记录被删了，这个哈希查不到，就只能和"Key 根本不存在"一样返回 401 —— 结果
   一样，但**你失去了追溯能力**：一把泄露的 Key 到底存在过没有、什么时候被吊销的、
   有多少数据是它上报的，全都查不出来了。
2. `api_keys.status` 的 CHECK 约束里本来就定义了 `'revoked'` 这个值。
   物理删除的话，这个状态永远写不进去，等于白定义。

> ⚠️ 配套约束：**列表接口默认只返回 `status = 'active'` 的 Key**。
> 否则用户会在界面上看到一堆已经吊销的 Key，分不清哪把还能用。
> 要展示吊销记录的话，那是另一个带筛选参数的接口的事（V1 不做）。
>
> ⚠️ 这是本模块**第二个越权入口**，而且比 `get_own_project` 那个更隐蔽 ——
> 路径 `/api-keys/{key_id}` 里没有「项目」这个词提醒你要校验归属。
> 它走 `Depends(get_own_api_key)`，查询里 join 到 `projects` 确认归属，
> 校验强度和 `get_own_project` 完全一致（不合规一律 404）。

## 3. 核心机制：用户隔离

这是本模块**最重要的设计**，其余模块都依赖它。

### 3.1 依赖链

```text
get_db              提供数据库会话
   ↓
get_current_user    解析 JWT → 得到 User 对象（未登录/无效 → 401）
   ↓
get_own_project     校验 project_id → 项目存在 且 属于当前用户（否则 → 404）
```

### 3.2 `get_own_project` 的契约

**输入**：路径参数 `project_id` + 当前用户
**输出**：Project 对象
**失败**：抛 404（**不是 403**）

```text
① project_id 对应的项目存在吗？      → 否：404
② 该项目的 owner_id == 当前用户 id？ → 否：404
```

**为什么失败返回 404**：403 等于告诉攻击者"这个 ID 存在，只是你没权限" —— 他可以用这个信息枚举出系统里所有项目 ID。统一返回 404，攻击者无法区分"不存在"和"不属于你"。

### 3.3 使用方式

所有涉及项目的接口（日志、统计、异常、模型分析……）**全部**通过它获取项目对象：

```text
@app.get("/api/v1/projects/{project_id}/logs")
def get_logs(project = Depends(get_own_project)):
    # 到这里 project 一定存在、且一定属于当前用户
```

> **这是本模块的核心价值**：把"记得校验归属"变成"结构上不可能忘"。
> 写 10 个接口，只要都用 `Depends(get_own_project)`，就不可能漏掉一个。

### 3.4 例外：不返回 project_id 的接口

`GET /api/v1/projects`（项目列表）不需要 `get_own_project`，但**必须**自己带 `owner_id` 过滤：

```text
WHERE owner_id = current_user.id
```

忘了这个条件 = 列出全系统所有项目。这是聚合区最典型的越权 bug。

## 4. 关键流程

### 4.1 创建项目

```text
① 校验当前用户的【活跃】项目数 < 上限（配置项，默认 3）
      否 → 400「项目数量已达上限（3 个），请先删除不再使用的项目」
② 校验同一用户下项目名不重复
      重复 → 400「同名项目已存在」
③ 插入 project 记录（owner_id = 当前用户）        ← flush() 拿 id，不提交
④ 生成 API Key：                                  ← 和 ③ 同一个事务
      key     = "proj_" + secrets.token_urlsafe(32)
      key_hash = SHA-256(key)
      存 key_hash + key_prefix（key 的前 12 位）
⑤ commit() —— 全流程唯一一次提交
⑥ 返回项目信息 + key 明文（仅此一次）
```

**① 只数 `status = 'active'` 的项目**，不是数所有项目：

```sql
SELECT count(*) FROM projects
WHERE owner_id = ? AND status = 'active'
```

需求文档 §3.5 说的是「最多 3 个**活跃**项目」。将来项目可以归档（`status='archived'`），
归档的项目不该继续占配额 —— 否则用户归档完还是建不了新的，归档就失去意义了。
V1 还没有归档入口，但配额口径现在就按这个写死，免得以后改的时候漏掉。

**① 在 ② 之前**：如果反了，配额满了但用户恰好输入了一个重名，会收到「同名项目已存在」——
他会去改名字，然后才发现真正的原因是配额满了。先把硬约束报出来，用户少走一趟。

**③ 和 ④ 必须同一个事务**。中间用 `flush()`（拿到自增 id，但不提交），
最后只 `commit()` 一次。图省事写成两次 commit 的话，第二次失败就会留下一个
**没有 Key 的孤儿项目** —— 用户看得见项目，却上报不了数据，而且没法自己修。

**第 ④ 步的细节**：

- 用 `secrets` 不用 `random` —— `random` 是可预测的伪随机
- 存哈希不存明文 —— 数据库泄露时无法反推可用 Key
- `key_prefix` 用于界面展示（让用户能区分是哪把 Key）

**为什么 API Key 用 SHA-256，而密码用 bcrypt**：

这是个容易搞反的地方 —— 两者都是「存哈希不存明文」，但选的算法应该相反：

| | 密码 | API Key |
|---|---|---|
| 算法 | **bcrypt** | **SHA-256** |
| 本机实测 | **213 ms / 次** | **0.0007 ms / 次**（快 30 万倍） |
| 攻击者能猜吗 | 能 —— 人类密码空间小，字典就几十亿条 | 不能 —— 256 位随机，穷举不可行 |
| 慢哈希有用吗 | **有**。慢 1000 倍 = 爆破成本高 1000 倍 | **没有**。反正猜不出来，慢只是白等 |
| 换算吞吐 | 4.7 次/秒 | 140 万次/秒 |

如果 API Key 也用 bcrypt：每次上报数据都要验一次 Key，那就是 **4.7 次/秒** ——
单个接入方的正常上报量就能把服务打满。而且这 213 ms 换不来任何安全性：
Key 是 256 位随机数，攻击者本来就猜不出来，让他「每个猜测慢 213 ms」毫无意义。

（上面是这台机器实测的数字。bcrypt 的耗时取决于 cost 因子，默认 12；
换台机器绝对值会变，但两者相差好几个数量级这个结论不变。）

反过来，密码**绝不能**用 SHA-256：它快到每秒能算几十亿次，配合彩虹表
几乎等于没加密。

> ⚠️ 第 ① 步有并发问题：两个请求同时通过校验可能创建出第 4 个项目。
> V1 单用户场景碰不上，**知道即可，不处理**。

### 4.2 登录

```text
① 按 username 查用户
② 校验密码（比对哈希）
      失败 → 401，错误信息统一为「用户名或密码错误」（不区分是哪个错）
③ 生成 JWT：payload 含 user_id、exp
④ 返回 token
```

> 第 ② 步的"不区分"也是安全设计：如果提示"用户名不存在"，攻击者就能用它枚举出系统里有哪些用户名。
>
> ⚠️ **密码长度必须在 ② 之前先判一次**。`bcrypt` 对超过 72 **字节**的输入直接抛
> `ValueError`，而且**登录路径也会抛** —— 因为 `checkpw()` 内部走的就是 `hashpw()`。
> 不预先判长度的话，用户拿一个超长密码来登录，服务端返回的是 500（服务器内部错误），
> 而不是 401。这是个能把监控页面刷满红色报错的坑。
>
> 判定要用 `len(password.encode("utf-8"))`，**不是 `len(password)`**：
> 上限的单位是字节，一个汉字在 UTF-8 里占 3 字节 —— 25 个汉字的密码（75 字节）
> 就已经超了，但 `len()` 看着才 25。
>
> 也不要「截断到 72 字节」来"兼容"：那会让"密码前 72 字节相同"的两个不同密码
> 变成同一个密码，是实打实的安全弱化。超长就直接拒绝。

### 4.3 删除项目

```text
① get_own_project 拿到项目
② 删除（V1 直接物理删除）
```

**要考虑的问题**：项目下的 `llm_requests` 怎么处理？

- 方案 A：级联删除（连同日志一起删）
- 方案 B：软删除项目，日志保留

**V1 选 A**（简单），在数据库外键上设置 `ON DELETE CASCADE`。

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 项目名重复 | 400，明确提示 |
| 超过项目数量上限 | 400，提示上限值 |
| 删除不存在的项目 | 404 |
| 删除别人的项目 | 404（同"不存在"） |
| API Key 过期 / 已吊销 | 401 |
| 未登录访问受保护接口 | 401 |
| 用户不存在时登录 | 401，「用户名或密码错误」 |
| 密码超过 72 字节 | 注册 422（入口拦）；登录 401（不抛 500） |
| 注册时 email 传空字符串 | 归一成 `NULL`（否则第二个空串会撞 UNIQUE 约束） |
| 字段超长（项目名 > 100 字符等） | 422 |

**最后一条要特别小心**：schema 里的 `max_length` 必须和数据库的 `VARCHAR(n)` **逐一对齐**。

```text
username    VARCHAR(50)   →  max_length=50
项目名      VARCHAR(100)  →  max_length=100
tech_stack  VARCHAR(50)   →  max_length=50
email       VARCHAR(255)  →  max_length=255
```

不写 `max_length` 的话，超长值会一路走到数据库才被拒绝，抛的是 `DataError` ——
用户拿到 500「服务器内部错误」，而这个错明明是他自己的输入问题，应该是 422。
**入口校验和数据库约束是两道独立的闸门，都要有**：前者给用户清晰的提示，
后者保证即使有人绕过 API 直接写库，数据也不会被写坏。

## 6. 实现顺序建议

按依赖关系自底向上：

```text
① config.py        配置管理（数据库 URL、JWT 密钥、项目上限）
② database.py      engine + SessionLocal + get_db
③ models/          User、Project、ApiKey 三张表
④ schemas/         请求/响应模型
⑤ deps.py          get_current_user、get_own_project
⑥ services/        认证、项目、API Key 的业务逻辑
⑦ api/             auth.py、projects.py
⑧ main.py          挂载路由
```

> **顺序不能乱**：③ 依赖 ①②，⑤ 依赖 ③④。从下往上写，每一层写完都能单独验证。

## 7. 需要安装的依赖

与 `ai-monitor-backend/pyproject.toml` 保持一致：

```text
bcrypt              密码哈希
fastapi             Web 框架
psycopg[binary]     PostgreSQL 驱动
pydantic-settings   配置管理
pyjwt               JWT 签发与校验
sqlalchemy          ORM
uvicorn[standard]   ASGI 服务器

（dev）httpx2         跑 TestClient 用 —— 见下面的说明
```

`pydantic` 本身没列进去：它是 `fastapi` 和 `pydantic-settings` 的依赖，
会被自动装上，显式再写一遍只会造成版本号两处维护。

> **`email` 字段是普通 `str`，不是 `EmailStr`**。用 `EmailStr` 要额外装
> `email-validator`，而且它会拒绝 `"abc"` 这种输入。
> V1 的 email 是**纯可选、且不承担任何功能**（不发验证邮件、不用于登录），
> 为它引一个依赖不划算。代价是数据库里可能存进格式不对的邮箱 ——
> 等真的要用 email 做点什么的时候（比如找回密码），再加 `EmailStr` 严格校验。
>
> **JWT 用 `pyjwt`，不用 `python-jose`**：`python-jose` 最后一次发版是 2021 年，
> 已基本停止维护；它有一个间接依赖 `ecdsa` 带过 CVE 历史。`pyjwt` 在活跃维护中，
> API 更小更直白，我们的用量（签发 + 校验 HS256）它完全够用。
>
> **密码哈希直接调 `bcrypt`，不用 `passlib`**：`passlib` 最后一次发版是 2020 年，
> 且与 `bcrypt` 4.x 及以上版本有已知的兼容性报错（它靠读 `bcrypt.__about__.__version__`
> 判断版本，而新版 bcrypt 已经移除了这个属性，一调用就报错）。
> `passlib` 的价值在于「一套 API 支持多种哈希算法」，但我们只用 bcrypt 一种 ——
> 为这点便利去背一个停止维护的中间层不划算。
> 代价是 `bcrypt` 的 72 字节限制要自己处理（见 §5）。
