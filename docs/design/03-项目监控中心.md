# 设计文档 03：项目监控中心

> 对应需求：[03-项目监控中心](../requirements/03-项目监控中心.md)
> 对应阶段：**阶段 7（Token / Cost 统计）、阶段 9（数据分析）**

------

## 1. 涉及的表

`llm_requests`（主）、`models`（成本计算时参考）。

本模块是**纯读**模块 —— 不写数据，只做聚合查询。

## 2. API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects/{project_id}/stats/overview` | 概览（区间汇总 + 环比 + 异常数） |
| GET | `/api/v1/projects/{project_id}/stats/tokens` | Token 统计 + 趋势 |
| GET | `/api/v1/projects/{project_id}/stats/costs` | 成本统计 + 趋势 |
| GET | `/api/v1/projects/{project_id}/stats/models` | 模型使用情况 |

**全部**通过 `Depends(get_own_project)` 获取项目 —— 这是隔离区的强制要求。

### 2.1 统一的时间范围参数

所有 stats 接口共用同一套参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `start_date` | datetime | 区间起点（含） |
| `end_date` | datetime | 区间终点（不含） |
| `granularity` | string | 分桶粒度，`day`（默认）或 `hour` |
| `tz` | string | 分桶时区，IANA 名，默认 `UTC` |

> **为什么不用 `range=today\|7d\|30d`**：
> 前端把快捷选项（今日 / 近 7 天 / 近 30 天）映射成具体的 start/end 即可，
> 后端只需要一套逻辑。而且以后要支持自定义时间范围时，不用改接口。

> **注意 end_date 是"不含"** —— 这是时间区间查询的惯例（左闭右开），
> 避免"10月1日到10月1日"这种语义歧义。

> ⚠️ **实现修订（阶段 7）：参数类型从 `date` 改为 `datetime`，并新增 `tz`。**
> 两个改动是同一个问题的两面：
>
> - **区间**用绝对时刻。裸日期无法表达"用户本地 0 点"，必须先约定它属于哪个时区，
>   而服务端无从得知用户的时区。改成让**前端把本地 0 点换算成 UTC 时刻再传过来**，
>   歧义就消失了 —— 这也让本接口与调用记录页的日期筛选完全同名同类型、同一套规则
>   （`_assume_utc`：不带时区的时间按 UTC 解释）。
>
> - **分桶**要按时区截断。区间用绝对时刻解决了"查哪一段"，但 §3.3 的按天聚合仍会
>   按数据库会话时区（UTC）切分，UTC+8 的用户会看到「今天」的数据被切一半到昨天 ——
>   实测项目 13 的数据，UTC 分桶下 10-10 有 11 次调用，按 `Asia/Shanghai` 是 13 次。
>   所以 `date_trunc('day', created_at)` 要写成
>   `(created_at AT TIME ZONE :tz)::date`，`tz` 由前端传
>   `Intl.DateTimeFormat().resolvedOptions().timeZone`。
>
> `tz` 非法时区名必须在 schema 层用 `zoneinfo` 挡成 422：漏到 PG 里是
> `InvalidParameterValue`，会冒泡成 500。顺带加了区间上限 3660 天 ——
> 补零骨架是按天逐个生成的，不设上限的话一个超长区间就能造出几十万个日期对象。

> ⚠️ **实现修订（2026-10-12）：新增 `granularity`。**
>
> 概览页的趋势图需要「选今天时看 24 小时」—— 按天分桶只会出 1 个点（见 §2.3）。
>
> - **粒度由前端给，服务端不按跨度自动推断**：「一天」是个本地日历概念，
>   服务端算不出用户那边的一天有多长（夏令时那天是 25 小时）。判定规则只有一份，
>   写在 `utils/timerange.ts` 的 `buildTimeRange` 里 —— 页面各自去判断的话，
>   迟早有一个页面判错。
> - **hour 有独立的跨度上限**：`end - start` 不得超过 1 天，超出 422。
>   实现上卡的是 `timedelta(days=1, hours=1)`，多留的 1 小时是给夏令时的：
>   秋令退那天本地日历日是 25 小时，按绝对时长卡死 24 小时的话，
>   「今日」在那些时区每年有一天会直接 422。
> - 前端的规则保证只有跨度正好 1 天才会传 `hour`，服务端这道校验是**防御** ——
>   不然直接调接口传一年 + `hour`，就是 8760 个点的响应。
> - `granularity` 对 overview / models **无效**：这两个接口不做分桶，收到就忽略。

### 2.2 overview 响应

```json
{
  "summary": {
    "calls": 110,
    "total_tokens": 600000,
    "cost": 1.54,
    "avg_latency": 2800
  },
  "previous": {
    "calls": 83,
    "total_tokens": 455000,
    "cost": 1.17,
    "avg_latency": 2600
  },
  "anomaly_count": null
}
```

> **这是聚合接口**：一次返回概览页需要的所有数据，而不是让前端发 3 个请求。
> 概览页是最高频访问的页面，减少往返次数对体验有实际影响。

> ⚠️ **实现修订（阶段 7）：`today` 改名为 `summary`，并新增 `previous`。**
>
> - `today` 这个名字在 §2.1 的「统一时间范围参数」下是错的 —— 用户选了近 30 天，
>   这个字段装的却是 30 天的汇总，不叫「今天」。默认选「今日」时它才恰好是今天。
>
> - `previous` 是**环比区间**的同口径指标，原型上那行「昨天 110 次 / ↗32%」
>   和需求 §4.1 的「相比上周 ↑32%」都要它，原设计里没有。口径定为
>   **上一个等长区间**：`[start, end)` 的环比区间是 `[start - (end - start), start)`。
>   一套逻辑覆盖今日 / 近 7 天 / 近 30 天 / 自定义，不用为每种快捷选项
>   单独定义「昨天」「上周」怎么算。百分比由前端算（不是金额，不涉及精度口径）。
>
> - `anomaly_count` 在阶段 9（异常分析）接上之前**恒为 `null`，不是 `0`** ——
>   前端据此区分「这个项目没有异常」和「异常功能还没做」，接上之后前端不用改。
>
> - `avg_latency` 在区间内**一次成功调用都没有时是 `null`**：没有可统计的响应时间，
>   和「响应时间是 0 毫秒」是两回事，后者在前端会被读成「快得离谱」。
>   失败调用不参与平均（§5.1），但**照常计入 calls / tokens / cost**。
>
> - ~~`recent_logs` 刻意**不按时间选择器过滤**：它是这个项目最新发生的调用，
>   选了「近 30 天」也不该看不见今天刚上报的那条。~~ 已删除，见下。

> ⚠️ **实现修订（2026-10-12）：`recent_logs` 删除。**
>
> 概览页原本在趋势图下面放了一块「最近调用」表格，后来整块去掉：想看最近调用
> 直接去「调用日志」页，那里的筛选和分页比概览页塞 5 行强；概览页也因此
> 一屏放得下（趋势图正好吃掉剩下的高度）。
>
> 删的是整条链路，不只是响应字段：`RecentLogItem`、`get_overview` 里那次
> **独立查询**（带 `load_only` 取 5 条）和它的回归用例一并删掉 ——
> 前端不用的数据，后端每请求多打一次库是纯浪费。

### 2.3 tokens / costs 响应（带趋势）

```json
{
  "summary": {
    "calls": 110,
    "input_tokens": 300000,
    "output_tokens": 300000,
    "total_tokens": 600000
  },
  "series": [
    {"date": "2026-10-01", "calls": 20, "total_tokens": 100000},
    {"date": "2026-10-02", "calls": 25, "total_tokens": 120000}
  ]
}
```

> `summary` 是区间汇总，`series` 是趋势 —— 一次返回，避免前端再发一次请求拿汇总。
>
> **趋势默认按天聚合**，但区间跨度正好是一个本地日历日时**按小时**（24 个点）。
>
> ⚠️ **实现修订（2026-10-12）：推翻原设计的「V1 不做按小时」。**
> 原判断（按小时的图在手机上看不清、"最近是不是越来越耗 Token"按天就能回答）
> 对「近 7 天 / 近 30 天」依然成立，但漏了一种情况：**用户只想看今天**。
> 单个日历日按天分桶只有一个点 —— 那不是趋势图，是个孤零零的圆点。
> 所以规则收紧成「跨度正好 1 天时按小时」，长区间仍按天，两者不冲突。
>
> `date` 字段是**标签字符串**，不是时刻：按天是 `"2026-10-01"`，
> 按小时是 `"2026-10-12T14:00"`。用 `str` 而不是 `date`/`datetime`，
> 是为了让两种粒度装进同一个字段，且前端不必去解析它 ——
> 解析就会踩 §3.3 末尾说的那两个 `new Date()` 坑。

> ⚠️ **实现修订（阶段 7）：补上 costs 的响应形状。**
> 原设计只给了 tokens 的示例，costs 与它同构：
>
> ```json
> {
>   "summary": {"calls": 110, "cost": 1.54},
>   "series": [{"date": "2026-10-01", "calls": 20, "cost": 0.28}]
> }
> ```
>
> `series` 里每天的 `cost` 之和**必须等于** `summary.cost` —— 两边口径不一致的话，
> 图上看到的和上面那个大数字会对不上，用户会以为其中一个算错了。
> 验收脚本里有一条断言专门锁这个。

### 2.4 models 响应

```json
{
  "items": [
    {
      "model": "deepseek-chat",
      "calls": 90,
      "total_tokens": 492000,
      "cost": 1.32,
      "avg_latency": 2600,
      "call_percentage": 82.0,
      "token_percentage": 61.4,
      "cost_percentage": 34.8
    }
  ]
}
```

> 三个百分比都由服务端算 —— 前端算会出现"总和不是 100%"的浮点问题，
> 而且成本占比属于「金额不做前端运算」那条约束的范围。
> 各项各自四舍五入到 1 位，加起来可能是 99.9 或 100.1，这是显示口径。

> ⚠️ **实现修订（2026-10-12）：`percentage` 拆成三个口径的字段。**
>
> 原设计只有 `percentage` 一个字段，按**调用次数**算。概览页要加「模型使用占比」
> 卡片、并且允许在调用次数 / Token / 成本三个口径之间切换，只有一个口径不够用了。
>
> - 字段名从 `percentage` 改成 `call_percentage`，和新加的两个对称 ——
>   留一个不带前缀的 `percentage` 再加两个带前缀的，看的人会以为前者是"总占比"。
> - **三套数是三套算法，不是一套抄三遍**：同一个模型按次数占 25%、按 Token 可能占 47%
>   （`gpt-4o` 这种情况很常见）。验收脚本里有一条断言专门锁这个 ——
>   它故意让某个模型每次调用的 Token 数更大，数据要是各模型 Token 数都一样，
>   两个口径会算出同一个值，那条断言就白测了。
> - 需求 §5.1 说的「使用 82%」现在对应 `call_percentage`。

> ⚠️ **实现修订（阶段 7）：未收录模型的 `cost` 是 `0`，不是 `null`。**
> `SUM` 跳过 NULL、`COALESCE` 兜底成 0。也就是说「这个模型的调用没配价格」
> 在成本列上会显示成 0 元 —— 这是 §5 边界表定的口径（跳过或按 0 计），
> **和「模型免费」看起来一样**。当前接受这个含混，因为混在一堆已知模型里
> 时，`null` 反而会丢掉已知部分的合计。真要区分得等到按模型单独标「价格未知」。
>
> `avg_latency` 与 §2.2 同理：该模型一次成功调用都没有时是 `null`。

## 3. 查询设计

### 3.1 依赖的索引

```text
llm_requests(project_id, created_at)
```

**本模块所有查询都必须带 `project_id`** —— 既是隔离要求，也正好命中索引的最左列。

### 3.2 概览查询（示意）

```sql
SELECT
  COUNT(*)                AS calls,
  COALESCE(SUM(total_tokens), 0)  AS total_tokens,
  COALESCE(SUM(estimated_cost), 0) AS cost,
  COALESCE(AVG(latency), 0)       AS avg_latency
FROM llm_requests
WHERE project_id = :project_id
  AND created_at >= :today_start
  AND created_at <  :tomorrow_start
```

> **`COALESCE` 的作用**：没有数据时 `SUM` 返回 `NULL`，前端拿到 null 会显示异常。
> 用 `COALESCE(..., 0)` 保证空数据时返回 0。

### 3.3 趋势分桶（PostgreSQL）

```sql
SELECT
  (created_at AT TIME ZONE :tz)::date AS day,
  COUNT(*) AS calls,
  SUM(total_tokens) AS total_tokens
FROM llm_requests
WHERE project_id = :project_id
  AND created_at >= :start
  AND created_at <  :end
GROUP BY day
ORDER BY day
```

> ⚠️ **`AT TIME ZONE :tz` 不能省（实现修订）**：直接对 `timestamptz` 取日期是按数据库
> 会话时区（UTC）截断的，UTC+8 的用户会看到「今天」的数据被切一半到昨天去。
> 实测项目 13 的数据：UTC 分桶下 10-10 有 11 次调用，按 `Asia/Shanghai` 是 13 次。
> 详见 §2.1。
>
> 返回的 `day` 是 `date` 而不是 `datetime`：前端拿到就是「哪一天」这个标签，
> 不涉及时刻，也就不会踩 `new Date('2026-10-01')` 按 UTC 解析、
> `new Date('2026-10-01T00:00:00')` 按本地解析的坑。

**按小时**只改分桶表达式，时区那一步完全相同：

```sql
SELECT
  date_trunc('hour', created_at AT TIME ZONE :tz) AS hour,
  ...
GROUP BY hour
ORDER BY hour
```

> ⚠️ **`AT TIME ZONE` 返回的是 `timestamp without time zone`（墙钟值）**，
> 驱动交回 Python 的是 **naive `datetime`（`tzinfo=None`）**。
> 所以 §3.4 生成小时骨架时**必须生成 naive 对象** —— 骨架挂着 `tzinfo` 的话，
> Python 里 `aware == naive` 恒为 `False`（**不报错**），补零查表会静默全部落空，
> 图上是一条 0 直线。（SQLAlchemy 侧：`created_at.op("AT TIME ZONE")(tz)`，
> 外面套 `func.date_trunc('hour', ...)` —— 后者在这个表达式上没有注册类型，
> 编译出来是 `NullType`，但生成的 SQL 正确，取值也不受影响。）

> **标签要抹掉秒**：`datetime.isoformat()` 默认给 `'2026-10-12T14:00:00'`，
> 而这是个给人看的标签，不是等着被解析回去的时刻 —— 用
> `isoformat(timespec="minutes")` 得到 `'2026-10-12T14:00'`。

### 3.4 ⚠️ 空的桶需要补零

如果 10 月 3 日没有调用，上面的查询**不会返回 10-03 这一行**。前端画图时这个桶会整个消失 —— x 轴上没有 10-03 的位置，读者会把 10-02 和 10-04 当成相邻的两天。

**解决方式**：服务端补零 —— 按区间生成完整的桶列表（按天是日期、按小时是整点），
把查询结果填进去，缺失的填 0。

> 这是统计类接口最常见的坑之一。放在服务端做，前端就能简单地直接渲染。
>
> 按小时时骨架的起点要 `replace(minute=0, second=0, microsecond=0)` ——
> 区间左端是前端的本地 0 点，但用户可能在一天中间发起请求，
> 不截断的话第一个桶的标签会带上分钟数，跟后续的整点对不上。

## 4. 缓存策略（阶段 8 引入 Redis 时）

**只缓存 overview**，其余不缓存。

| 接口 | 缓存 | TTL | 理由 |
|---|---|---|---|
| overview | ✅ | 60 秒 | 高频访问，短时间不要求精确到秒 |
| tokens / costs / models | ❌ | —— | 参数组合多，命中率低；查询本身不慢 |

### 4.1 缓存键设计

```text
stats:overview:{project_id}:{start_date}:{end_date}:{tz}
```

> ⚠️ **实现修订（阶段 7）：键里必须带区间和时区。**
> 原设计的 `stats:overview:{project_id}` 在「所有 stats 接口共用 start/end」的约定下
> 会串数据 —— 用户切到近 30 天，拿到的还是 60 秒前「今日」的缓存。
> **键要覆盖所有影响结果的参数**，这是缓存的通用规则。

### 4.2 ⚠️ 失效时机

**不能只靠 TTL 过期** —— 用户刚上报了数据，回到页面却看到 60 秒前的旧数据，会以为系统坏了。

```text
上报接口写入成功后 → 删除 stats:overview:{project_id}:*
```

> 删除要用**前缀匹配**（`SCAN` + `DEL`，不用 `KEYS` —— 后者会阻塞整个库）：
> 一个项目同时有多个区间和时区的缓存条目，全都要失效。

> 这就是"缓存失效"的典型处理：**写时删除，读时重建**（Cache-Aside 的写策略）。
> 它是缓存一致性问题最简单的解法，V1 用它就够了。

> ⚠️ 如果阶段 8 发现"没有性能问题"，**这一步可以跳过**。
> 不要为了用 Redis 而用 Redis —— 引入缓存就是引入了新的 bug 来源。

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 区间内无任何数据 | 返回 0 和空数组，不报错；趋势仍按桶补零 —— 缺一个桶会被读成「没有这一天」，而不是「这天是 0」 |
| 只有失败调用 | calls / tokens / cost 照常统计（失败的调用也烧了钱），`avg_latency` 为 `null` |
| `estimated_cost` 为 null（未知模型） | 求和时跳过，合计按 0 计（见 §2.4 的说明） |
| `end_date <= start_date` | 422，参数校验直接拒绝 |
| 时间跨度过大 | ⚠️ **实现修订**：由「V1 不限制」改为**上限 3660 天（约 10 年）**，超出 422。原判断只考虑了 SQL 的代价，漏了补零骨架是按天在 Python 里逐个生成的 —— 不设上限时一个超长区间就能造出几十万个日期对象 |
| `granularity=hour` 但跨度 > 1 天 | 422。上限卡 `timedelta(days=1, hours=1)`，多留 1 小时给夏令时（§2.1） |
| 跨度正好 1 天的趋势 | 按小时返回 24 个点，而不是 1 个点（§2.3） |
| 概览页自定义范围跨度 > 30 天 | 前端拦下并提示「时间跨度不能超过 30 天」，**不发请求**。这条限制只在概览页 —— 日志页是分页列表，翻半年前的数据是合理需求，不受限 |
| `tz` 不是合法时区名 | 422，在 schema 层用 `zoneinfo` 挡（漏到 PG 里是 500） |
| 项目刚创建，无数据 | 同"无数据" |

### 5.1 平均响应时间该不该计入失败调用？

**建议：只统计成功的调用。**

失败请求（如超时）的 latency 可能是超时时间本身（30s），把它算进平均值会让"平均响应时间"这个指标失真 —— 用户看到的数字无法反映正常体验。

> 这是**指标口径**问题。要在响应里或用文档说清楚口径，否则用户会对不上数。

## 6. 实现顺序建议

```text
① services/stats.py     聚合查询（先用一段脚本直接跑 SQL 验证结果对不对）
② schemas/stats.py      响应模型
③ api/stats.py          路由
④ 逐页面前端对接
```

> **建议先写一个临时的查询脚本**，把 SQL 跑通、看着数据对得上，再做接口。
> 直接在接口里调 SQL 会很难调试 —— 出问题时你不知道是 SQL 错了还是路由错了。

> ✅ **实现完成（阶段 7）**：四个接口全部就位，`scripts/check_stats.py` 12/12 全绿。

> 就是在对账时用真实数据看出来的，不是靠推理发现的）。
