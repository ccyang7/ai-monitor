# 设计文档 03：项目监控中心

> 对应需求：[03-项目监控中心](../requirements/03-项目监控中心.md)
> 对应阶段：**阶段 7（Token / Cost 统计）、阶段 9（数据分析）**

------

## 1. 涉及的表

`llm_requests`（主）、`models`（成本计算时参考）。

本模块是**纯读**模块 —— 不写数据，只做聚合查询。

------

## 2. API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects/{project_id}/stats/overview` | 概览（今日指标 + 最近调用 + 异常数） |
| GET | `/api/v1/projects/{project_id}/stats/tokens` | Token 统计 + 趋势 |
| GET | `/api/v1/projects/{project_id}/stats/costs` | 成本统计 + 趋势 |
| GET | `/api/v1/projects/{project_id}/stats/models` | 模型使用情况 |

**全部**通过 `Depends(get_own_project)` 获取项目 —— 这是隔离区的强制要求。

### 2.1 统一的时间范围参数

所有 stats 接口共用同一套参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `start_date` | date | 开始日期（含） |
| `end_date` | date | 结束日期（不含） |

> **为什么不用 `range=today\|7d\|30d`**：
> 前端把快捷选项（今日 / 近 7 天 / 近 30 天）映射成具体的 start/end 即可，
> 后端只需要一套逻辑。而且以后要支持自定义时间范围时，不用改接口。

> **注意 end_date 是"不含"** —— 这是时间区间查询的惯例（左闭右开），
> 避免"10月1日到10月1日"这种语义歧义。

### 2.2 overview 响应

```json
{
  "today": {
    "calls": 110,
    "total_tokens": 600000,
    "cost": 1.54,
    "avg_latency": 2800
  },
  "recent_logs": [
    {
      "id": 1024,
      "model": "deepseek-chat",
      "total_tokens": 18293,
      "latency": 2800,
      "status": "success",
      "created_at": "2026-10-08T11:42:31Z"
    }
  ],
  "anomaly_count": 3
}
```

> **这是聚合接口**：一次返回概览页需要的所有数据，而不是让前端发 3 个请求。
> 概览页是最高频访问的页面，减少往返次数对体验有实际影响。

### 2.3 tokens / costs 响应（带趋势）

```json
{
  "summary": {
    "calls": 110,
    "input_tokens": 300000,
    "output_tokens": 300000,
    "total_tokens": 600000
  },
  "series": [
    {"date": "2026-10-01", "calls": 20, "total_tokens": 100000},
    {"date": "2026-10-02", "calls": 25, "total_tokens": 120000}
  ]
}
```

> `summary` 是区间汇总，`series` 是按天的趋势 —— 一次返回，避免前端再发一次请求拿汇总。
>
> **趋势按天聚合**，V1 不做按小时（真实场景下按小时的图在手机上看不清，而"最近是不是越来越耗 Token"这个产品问题按天就能回答）。

### 2.4 models 响应

```json
{
  "items": [
    {
      "model": "deepseek-chat",
      "calls": 90,
      "total_tokens": 492000,
      "cost": 1.32,
      "avg_latency": 2600,
      "percentage": 82.0
    }
  ]
}
```

> `percentage` 由服务端算 —— 前端算会出现"总和不是 100%"的浮点问题。

## 3. 查询设计

### 3.1 依赖的索引

```text
llm_requests(project_id, created_at)
```

**本模块所有查询都必须带 `project_id`** —— 既是隔离要求，也正好命中索引的最左列。

### 3.2 概览查询（示意）

```sql
SELECT
  COUNT(*)                AS calls,
  COALESCE(SUM(total_tokens), 0)  AS total_tokens,
  COALESCE(SUM(estimated_cost), 0) AS cost,
  COALESCE(AVG(latency), 0)       AS avg_latency
FROM llm_requests
WHERE project_id = :project_id
  AND created_at >= :today_start
  AND created_at <  :tomorrow_start
```

> **`COALESCE` 的作用**：没有数据时 `SUM` 返回 `NULL`，前端拿到 null 会显示异常。
> 用 `COALESCE(..., 0)` 保证空数据时返回 0。

### 3.3 按天趋势（PostgreSQL）

```sql
SELECT
  date_trunc('day', created_at) AS day,
  COUNT(*) AS calls,
  SUM(total_tokens) AS total_tokens
FROM llm_requests
WHERE project_id = :project_id
  AND created_at >= :start
  AND created_at <  :end
GROUP BY day
ORDER BY day
```

### 3.4 ⚠️ 空日期需要补零

如果 10 月 3 日没有调用，上面的查询**不会返回 10-03 这一行**。前端画折线图时会出现断点。

**解决方式**：服务端补零 —— 按日期范围生成完整日期列表，把查询结果填进去，缺失的填 0。

> 这是统计类接口最常见的坑之一。放在服务端做，前端就能简单地直接渲染。

## 4. 缓存策略（阶段 8 引入 Redis 时）

**只缓存 overview**，其余不缓存。

| 接口 | 缓存 | TTL | 理由 |
|---|---|---|---|
| overview | ✅ | 60 秒 | 高频访问，短时间不要求精确到秒 |
| tokens / costs / models | ❌ | —— | 参数组合多，命中率低；查询本身不慢 |

### 4.1 缓存键设计

```text
stats:overview:{project_id}
```

### 4.2 ⚠️ 失效时机

**不能只靠 TTL 过期** —— 用户刚上报了数据，回到页面却看到 60 秒前的旧数据，会以为系统坏了。

```text
上报接口写入成功后 → 删除 stats:overview:{project_id}
```

> 这就是"缓存失效"的典型处理：**写时删除，读时重建**（Cache-Aside 的写策略）。
> 它是缓存一致性问题最简单的解法，V1 用它就够了。

> ⚠️ 如果阶段 8 发现"没有性能问题"，**这一步可以跳过**。
> 不要为了用 Redis 而用 Redis —— 引入缓存就是引入了新的 bug 来源。

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 区间内无任何数据 | 返回 0 和空数组，不报错 |
| 只有失败调用 | Token 统计正常（失败的调用也有 Token 消耗） |
| `estimated_cost` 为 null（未知模型） | 求和时跳过，或按 0 计 |
| `start_date > end_date` | 422，参数校验直接拒绝 |
| 时间跨度过大（如 10 年） | V1 不限制，按天聚合的数据量可控 |
| 项目刚创建，无数据 | 同"无数据" |

### 5.1 平均响应时间该不该计入失败调用？

**建议：只统计成功的调用。**

失败请求（如超时）的 latency 可能是超时时间本身（30s），把它算进平均值会让"平均响应时间"这个指标失真 —— 用户看到的数字无法反映正常体验。

> 这是**指标口径**问题。要在响应里或用文档说清楚口径，否则用户会对不上数。

## 6. 实现顺序建议

```text
① services/stats.py     聚合查询（先用一段脚本直接跑 SQL 验证结果对不对）
② schemas/stats.py      响应模型
③ api/stats.py          路由
④ 逐页面前端对接
```

> **建议先写一个临时的查询脚本**，把 SQL 跑通、看着数据对得上，再做接口。
> 直接在接口里调 SQL 会很难调试 —— 出问题时你不知道是 SQL 错了还是路由错了。
