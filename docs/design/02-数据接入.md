# 设计文档 02：数据接入

> 对应需求：[02-数据接入](../requirements/02-数据接入.md)
> 对应阶段：**阶段 6**

------

## 1. 核心区别：两套凭证

这是本模块最容易搞混的地方 —— 平台有**两套完全不同的认证**：

| | 用户接口 | 上报接口 |
|---|---|---|
| 谁在用 | 平台的前端 | 接入方的 AI 项目 |
| 凭证 | JWT（用户登录得到） | **API Key**（项目创建时生成） |
| 传递方式 | `Authorization: Bearer <token>` | `X-API-Key: proj_xxx` |
| 识别出 | 用户 | **项目** |
| 失败返回 | 401 | 401 |

> **为什么分开**：JWT 代表"某个人登录了"，API Key 代表"某个项目在汇报数据"。两者语义不同，混用会导致权限模型混乱。

------

## 2. API 接口

| 方法 | 路径 | 认证 |
|---|---|---|
| POST | `/api/v1/logs` | `X-API-Key` |

### 2.1 请求体

```json
{
  "provider": "deepseek",
  "model": "deepseek-chat",
  "input": "什么是 Redis？",
  "output": "Redis 是一种开源的...",
  "input_tokens": 382,
  "output_tokens": 901,
  "total_tokens": 1283,
  "latency": 1820,
  "status": "success",
  "error": null,
  "timestamp": "2026-10-06T11:42:31Z"
}
```

### 2.2 字段校验规则

| 字段 | 必填 | 校验 |
|---|---|---|
| provider | 是 | 非空 |
| model | 是 | 非空 |
| input | 是 | 可空字符串 |
| output | 否 | 可空（失败调用无输出） |
| input_tokens | 否 | ≥ 0，默认 0 |
| output_tokens | 否 | ≥ 0，默认 0 |
| total_tokens | 否 | ≥ 0，默认 0 |
| latency | 是 | ≥ 0，单位毫秒 |
| status | 是 | `success` / `error` |
| error | 否 | 可空 |
| timestamp | 否 | 不传则用服务端时间 |

> **设计原则：宽进严出。** 上报字段尽量给默认值，不要因为非关键字段缺失就拒绝整条日志 —— 数据丢了比数据不全更糟。

### 2.3 响应

```json
// 201
{"id": 1024, "project_id": 1, "created_at": "2026-10-06T11:42:31Z"}
```

### 2.4 错误

| 情况 | 状态码 | 说明 |
|---|---|---|
| 缺少 / 无效 API Key | 401 | |
| Key 已吊销 / 过期 | 401 | |
| 必填字段缺失 | 422 | FastAPI 自动生成 |
| 字段格式错误（如 latency 为负） | 422 | |

------

## 3. 处理流程

```text
① 从 X-API-Key 头取 Key
② 哈希 → 查 api_keys 表（key_hash 唯一索引）
③ 校验 status == active 且未过期
      失败 → 401
④ 得到 project_id
⑤ 计算成本快照（见 §4）
⑥ 组装 LLMRequest 记录，写入 llm_requests
⑦ 返回 201
```

### 3.1 为什么第 ② 步是哈希后查

`api_keys` 表存的是 `key_hash`，不是明文。所以查询时：

```text
收到 key → 计算哈希 → WHERE key_hash = :hash
```

而不是 `WHERE api_key = :key`。

> 这也意味着**哈希算法必须确定**（不能用加盐哈希，否则每次算出来不一样，无法查询）。
> 密码用加盐哈希（每次盐不同），API Key 用**固定的 SHA-256**（因为需要能查到）。
> 这两者的区别值得记住：**密码是"验证"，Key 是"查找"。**

------

## 4. 成本快照计算

写入时按当时的模型价格算好 `estimated_cost` 存进记录。

```text
① 用请求的 model 字段匹配 models 表的 model_name
      ↓
   没匹配到 → estimated_cost = null（不报错、不拒绝写入）
      ↓
② 计算：
   estimated_cost = input_tokens  / 1_000_000 × input_price
                  + output_tokens / 1_000_000 × output_price
```

### 4.1 匹配规则

```text
WHERE model_name = :model
  AND status = 'active'
  AND (is_builtin = true OR owner_id = :key 对应项目的 owner_id)
```

> 注意最后那个条件 —— 用户自建的模型价格只对他自己的项目生效。
> 但上报接口**没有用户上下文**（只有 Key → 项目），所以需要"项目 → owner_id → 用户"再查模型。

### 4.2 ⚠️ 未知模型必须容忍

模型表里没有这个模型时：

```text
❌ 拒绝写入 → 数据丢失，且接入方不知道为什么
✅ 照常写入，estimated_cost = null → 统计时成本显示为 0 或「未知」
```

**数据完整性优先于成本计算。** 用户可能用了新模型还没配价格，这种情况下日志仍然要记录。

## 5. 性能考虑

上报接口会被**高频调用**（每次 LLM 调用一次），设计上要注意：

| 点 | 做法 |
|---|---|
| `api_keys(key_hash)` 唯一索引 | 每次上报都要查一次，必须走索引 |
| 避免在写入路径做重计算 | 成本计算是几次乘加，可接受；不要在这里做统计聚合 |
| 批量上报 | V1 不做，但字段设计上允许后续扩展为数组 |

### 5.1 关于批量上报

接入方在高峰期可能每秒产生多次调用。逐条 POST 会产生大量小请求。

**V1 先做单条**（简单、好调试）。如果实际发现请求量太大，再扩展为接受数组：

```json
{"logs": [ {...}, {...} ]}
```

这是**向后兼容**的扩展（新增方式，不破坏已有的单条接口），所以现在不做不会有代价。

## 6. 数据播种脚本（开发期必需）

**这是本模块的一个重要产出物** —— 开发阶段 7 之后的所有功能（统计、图表、异常、AI 分析）都需要数据来验证，但真实接入是后面的事。

### 6.1 脚本职责

```text
生成 N 条看起来真实的 llm_request 记录：
  - 跨越最近 30 天
  - 2～3 个不同模型
  - 时间分布模拟真实使用（白天多、夜里少）
  - 90% 成功，10% 失败（带各种错误信息）
  - 大部分 Token 在 1K～5K，夹杂少数 20K+ 的异常样本
  - 响应时间 1s～4s，夹杂少数 15s+ 的慢请求
```

### 6.2 为什么这个脚本很重要

| 没有它 | 有它 |
|---|---|
| 图表全是 0，不知道对不对 | 能立刻看出统计逻辑错没错 |
| 没法验证异常检测 | 有已知的异常样本可以验证 |
| AI 助手查出来的都是空 | 助手能给出真实分析 |

### 6.3 放在哪

```text
ai-monitor-backend/scripts/seed_data.py
```

> 这个脚本属于**开发工具**，不是生产代码 —— 但它应该提交进仓库，因为换台机器开发时还要用。

## 7. 实现顺序建议

```text
① models/llm_request.py    日志表
② services/ingest.py       上报业务逻辑（鉴权 + 成本计算 + 写入）
③ schemas/log.py           请求/响应模型
④ api/logs.py              路由
⑤ scripts/seed_data.py     数据播种
```

## 8. 边界情况

| 情况 | 处理 |
|---|---|
| API Key 无效 | 401，不回显 Key 内容 |
| Key 有效但项目已删除 | 401 |
| 模型表里没有该模型 | 正常写入，cost = null |
| timestamp 是未来时间 | V1 接受，不校验（接入方时钟可能不准） |
| input / output 超长 | 设置合理上限（如 text 类型可容纳），超限截断并记录 |
| 同一请求重复上报 | V1 不处理幂等（接入方自己保证重试逻辑） |
