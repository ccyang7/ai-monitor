## 1. API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects/{project_id}/logs` | 日志列表（筛选 + 分页） |
| GET | `/api/v1/logs/{log_id}` | 日志详情 |

### 1.1 列表接口的查询参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 页码 |
| `page_size` | int | 20 | 每页条数，上限 100 |
| `model` | str | —— | 按模型筛选 |
| `status` | str | —— | `success` / `error` |
| `start_date` | datetime | —— | 开始时间（**含**） |
| `end_date` | datetime | —— | 结束时间（**不含**） |
| `min_tokens` | int | —— | 总 Token 下限 |
| `max_tokens` | int | —— | 总 Token 上限 |
| `q` | str | —— | 关键词搜索（input / output） |

> **筛选条件全部可选**，不传就是不过滤。后端把它们按需拼进 `WHERE`，**始终与 `project_id` 是 AND 关系**。

> ⚠️ **实现修订（阶段 7）：时间区间统一成左闭右开 `[start_date, end_date)`。**
> 与[设计 03 §2.1](03-项目监控中心.md)的 stats 接口同一套语义 —— 前端传「本地某天 0 点」
> 到「次日 0 点」这两个绝对时刻，后端用 `< end_date` 正好含满最后一天。
>
> 原实现是后端 `<= end_date`、前端配套传 `23:59:59.999`，两个问题：一是
> 那一毫秒之后、午夜之前的记录会被漏掉；二是同一个「选一天」的语义在日志页和概览页
> 要靠两套不同的边界处理，迟早会写错一边。现在改只动 [check_logs.py](../../ai-monitor-backend/scripts/check_logs.py)
> 里两条用例，等接入方多起来就不是这个价了。

### 1.2 列表响应

```json
{
  "items": [
    {
      "id": 1024,
      "model": "deepseek-chat",
      "input_tokens": 382,
      "output_tokens": 901,
      "total_tokens": 1283,
      "latency": 1820,
      "status": "success",
      "estimated_cost": 0.0082,
      "created_at": "2026-10-06T11:42:31Z"
    }
  ],
  "total": 1350,
  "page": 1,
  "page_size": 20
}
```

> ⚠️ **列表不返回 `input` / `output`** —— 这两个是大文本字段，列表里带了会让响应体积暴增（一页 20 条可能几 MB）。列表只给摘要，详情才取全文。

### 1.3 详情响应

在列表字段基础上增加：

```json
{
  "provider": "deepseek",
  "input": "什么是 Redis？",
  "output": "Redis 是一种开源的...",
  "error_message": null
}
```

## 2. 详情接口的隔离问题（重要）

详情接口的路径是 `/api/v1/logs/{log_id}` —— **注意它没有 `project_id` 参数**。

这意味着**不能用 `Depends(get_own_project)`**，需要另一种隔离方式：

```text
① 查 log_id 对应的日志
② 通过 log.project_id 查出项目
③ 校验项目的 owner_id == 当前用户
④ 任一环节不通过 → 404
```

### 2.1 为什么不用嵌套路径

也可以用 `/api/v1/projects/{project_id}/logs/{log_id}`，那样就能直接用 `get_own_project`。

两种都可行，V1 选扁平路径，但**必须自己写归属校验**。

> **这正说明隔离不能只靠一个依赖函数** —— 依赖能覆盖大部分接口，但总有例外。
> 例外处必须**显式**写校验，并且要在 Code Review 时重点检查。

### 2.2 建议做法

抽一个 `get_own_log(log_id, current_user)` 依赖，逻辑同上，让详情接口也能用 `Depends`：

```text
def get_own_log(log_id: int, user = Depends(get_current_user)) -> LLMRequest:
    # 查日志 → 查其项目 → 校验 owner_id
    # 不通过 → 404
```

> **规律**：每多一个"通过 ID 直接访问资源"的接口，就多一个越权风险点。
> 遇到这类接口时，第一反应应该是"怎么用依赖把它也管起来"。

## 3. 搜索实现

### 3.1 搜索范围

```text
input       用户输入
output      AI 输出
model       模型名称
```

### 3.2 实现方式

PostgreSQL 用 `ILIKE`（不区分大小写的模糊匹配）：

```sql
WHERE (
    input  ILIKE '%' || :q || '%'
 OR output ILIKE '%' || :q || '%'
 OR model  ILIKE '%' || :q || '%'
)
```

### 3.3 ⚠️ 性能提示

`ILIKE '%关键词%'` 是**全表扫描** —— 前置通配符让索引完全用不上。

| 数据量 | 表现 |
|---|---|
| 几千条 | 无感 |
| 几万条 | 开始明显 |
| 几十万条 | 不可接受 |

**V1 接受这个代价**（数据量可控），但要记得它是已知的技术债。

后续优化方向：

```text
pg_trgm 扩展 + GIN 索引     → 支持 LIKE 的模糊索引
tsvector 全文检索           → 更适合"搜关键词"的场景
```

### 3.4 搜索的边界

- **空字符串要跳过** —— `q=""` 时不要拼进 WHERE，否则会变成全表扫描
- **限制搜索词长度**（如 100 字符），避免超长输入
- 搜索时**不支持正则 / 特殊符号**，当作纯文本处理

## 4. 分页设计

### 4.1 参数校验

```text
page >= 1
1 <= page_size <= 100
```

上限 100 是**保护措施** —— 不限制的话，一个 `page_size=1000000` 的请求就能把数据库拖垮。

### 4.2 排序

固定按 `created_at DESC, id DESC` 排序。

> **为什么要带 `id` 做第二排序键**：如果同一毫秒有多条记录，只按 `created_at` 排序结果不稳定 ——
> 翻页时可能出现某条记录在第 1 页和第 2 页都出现（或都不出现）。加 `id` 保证排序确定。

### 4.3 总数查询

`total` 需要单独的 `COUNT(*)` 查询，条件与列表一致（去掉分页）。

**V1 不管优化问题** —— 数据量大到需要"估算总数"时再说。

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 查询不存在的 log_id | 404 |
| 查询别人的日志 | 404 |
| `page` 超出总页数 | 返回空数组 + 正确的 total |
| `min_tokens > max_tokens` | 422，校验拒绝 |
| `start_date > end_date` | 422 |
| 搜索词含 `%` 或 `_` | 需要转义，否则会被当成通配符 |
| input / output 为 null | 搜索时用 `COALESCE` 处理 |

> **`%` 和 `_` 的转义**是 LIKE 查询的经典坑：用户搜 "50%"，如果不转义，`%` 会被当成通配符，搜出一堆无关记录。

## 6. 实现顺序建议

```text
① services/logs.py      列表查询（条件组装）+ 详情查询
② schemas/log.py        分页响应模型
③ api/logs.py           两个路由 + get_own_log 依赖
④ 用播种数据验证筛选组合
```

### 6.1 调试建议

筛选条件多，组合爆炸。**写完后要逐个参数单独测一遍**，再测几个组合：

```text
只带 model / 只带 status / 只带时间范围 / 只带搜索词
model + status / 时间 + 搜索 / 全部一起
```

用 `/docs` 页面点点就能测 —— 这是 FastAPI 自动文档最实用的地方。
