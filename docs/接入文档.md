# 接入文档：把 AI 项目的调用上报到 AI Monitor

> 面向：准备把自己 AI 项目的模型调用接入本平台的开发者。
> 对应需求：[02-数据接入](requirements/02-数据接入.md) ｜ 对应设计：[02-数据接入](design/02-数据接入.md)
> 本平台自身的开发文档在 `docs/requirements/` 与 `docs/design/`，那是「怎么做这个平台」；本文是「怎么用它」。

------

## 0. 接入方式：HTTP 上报，没有 SDK

平台**不提供 SDK，也不做代理层**。接入动作只有一件事：

> 在你的 AI 项目里，**一次模型调用完成之后**，往平台发一个 HTTP POST。

```
你的 AI 项目 ──POST /api/v1/logs──> AI Monitor
   （一次调用结束）
```

**为什么不做 SDK**：接入方跨语言（Python / Java / 前端），维护多套 SDK 的成本远大于收益，而接口本身只有一个。

**为什么不做代理层**：代理意味着**平台变成了你业务的关键路径** —— 平台一挂，你的 AI 项目就调不动模型了。这和本平台的第一原则冲突：**监控平台不可用时，接入方的 AI 项目必须照常运行。**

------

## 1. 接入前的准备

分两侧：**平台侧**是登录平台点几下，**接入方侧**是定三件事。

### 1.1 平台侧

#### 第 1 步：确认平台服务连得上

```bash
curl http://<平台地址>:8001/health
# 期望：{"status":"ok"}
```

> ⚠️ **注意 `health` 在根路径**，不在 `/api/v1` 下面 —— 业务接口都在 `/api/v1/` 前缀下，健康检查是唯一的例外。
>
> `8001` 是本项目本地开发用的端口（本机 8000 被另一个项目占了）。实际端口以平台部署者给你的为准。

**如果平台和你的 AI 项目不在同一台机器上**，平台必须以 `--host 0.0.0.0` 启动，并且放行对应端口。

> ⚠️ uvicorn 默认只绑回环地址（`127.0.0.1`）。没绑对外地址时，症状很有迷惑性：**你的项目报「连接被拒绝」，而平台的日志里一条请求都没有** —— 看起来像平台的 bug，实际是它根本没收到包。排查时先确认这个，不要一上来就怀疑接口。

#### 第 2 步：注册账号、创建项目

平台以**项目（Project）**为隔离单位。登录后在首页创建项目，**每个用户最多 3 个活跃项目**。

> **一个 AI 项目对应一个平台项目。** 不要让多个 AI 项目共用一个平台项目 —— 调用记录、成本、统计会全部混在一起，而且事后没法拆开。

#### 第 3 步：新建 API Key

进入该项目的「设置」页 → 新建 Key → 复制明文。

> ⚠️ **Key 的明文只在创建的那一刻显示一次**，之后平台只保留哈希和前缀，再也拿不到完整值。错过了就吊销重建一把。
>
> 平台存的是 **SHA-256 哈希**，不存明文 —— 所以「忘记 Key 了帮我查一下」这件事在平台侧是做不到的，这是有意的设计。

拿到形如 `proj_` 开头的 48 位字符串后，**存进你项目的 `.env`**：

```bash
AI_MONITOR_BASE_URL=http://<平台地址>:8001
AI_MONITOR_API_KEY=proj_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

> ⚠️ **Key 不要写进代码，不要提交进 Git。** `.env` 要加进 `.gitignore`。

Key 可以在「设置」页随时吊销。吊销后立即失效，上报会返回 401。

#### 第 4 步（最容易漏）：确认模型价格已配置

平台靠**模型名**去价格表里查单价来算成本。

**模型名对不上时，日志照常入库，但 `estimated_cost` 是空的** —— 调用记录页那一列显示「—」。

平台内置的模型（见 `ai-monitor-backend/scripts/init_models.py`）：

| provider | 模型名 | 输入（元/百万 token） | 输出（元/百万 token） |
|---|---|---|---|
| deepseek | `deepseek-chat` | 1 | 2 |
| deepseek | `deepseek-reasoner` | 4 | 16 |
| deepseek | `deepseek-v4-flash` | 1 | 2 |
| openai | `gpt-4o` | 18 | 72 |
| openai | `gpt-4o-mini` | 1.1 | 4.4 |
| siliconflow | `BAAI/bge-m3` | 0 | 0 |

> ⚠️ **`BAAI/bge-m3` 的那两个 0 是真实价格，不是没填** —— 该模型在硅基流动上免费，且嵌入调用没有 output token，所以输入输出都是 0。
>
> 由此带来一个容易误判的地方：**它的成本列显示 `¥0.00`，这和模型名未收录时显示的「—」是两回事。** `¥0.00` = 算出来了、结果是 0；`—` = 查不到价格、算不了。接入免费模型时，别把 `¥0.00` 当成「没配上」去排查。

你的模型不在表里，有两条路：

- **能接受没有成本**：直接接。成本列显示「—」，其余统计与筛选不受影响
- **要算成本**：往 `models` 表加一行。**模型名必须与上报的 `model` 字段逐字一致**（大小写敏感），否则查不到

### 1.2 接入方侧：定三件事

#### ① 上报时机 —— 调用**完成后**再报

不要在调用前报。调用完成才有 `output`、`tokens`、`latency`、`status` 这四个字段的值。

#### ② 上报**不能阻塞、不能抛异常**

这是接入的头号要求，也是最容易翻车的地方。

- 放**后台线程 / 异步任务**，不要在请求主链路上同步等待
- 设一个**短超时**（2~5 秒足够）
- **所有异常就地吞掉**，只记本地日志，绝不往上抛

> ⚠️ 最常见的事故不是「平台挂了」，而是**接入方把上报写成了同步调用**。平台一重启，你的 AI 项目跟着一起挂 —— 监控系统反过来搞死了被监控的系统。
>
> 所以第 4 节把「关掉平台再跑一次业务」列为**必测项**。

#### ③ 失败调用**也要上报**

`status="error"` 的调用是异常分析的主要来源。只报成功的调用，等于把「出问题的那部分」全部藏起来。

## 2. 接口契约

### 2.1 请求

```
POST  {平台地址}/api/v1/logs
X-API-Key: proj_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Content-Type: application/json
```

**认证与用户登录完全分离**：业务页面用 JWT（`Authorization: Bearer`），上报接口用 `X-API-Key`。语义不同 —— 一个是「人登录」，一个是「程序汇报」。

### 2.2 请求字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `provider` | string | ✅ | 供应商，如 `deepseek`。1~50 字符 |
| `model` | string | ✅ | 模型名，如 `deepseek-v4-flash`。1~100 字符。**要与价格表一致才能算出成本** |
| `latency` | int | ✅ | **耗时，单位毫秒**（≥ 0） |
| `status` | string | ✅ | 只有 `success` / `error` 两个值 |
| `input_tokens` | int | | 输入 token，默认 0（≥ 0） |
| `output_tokens` | int | | 输出 token，默认 0（≥ 0） |
| `total_tokens` | int | | 不传时由服务端用 `input_tokens + output_tokens` 补齐。**建议不传** |
| `input` | string \| null | | 提问原文 / 提示词。列表页不返回它，只有详情抽屉里能看 |
| `output` | string \| null | | 模型回答原文，同上 |
| `error` | string \| null | | `status="error"` 时的错误信息 |
| `timestamp` | datetime | | 调用发生时间（ISO 8601）。不传则取服务端当前时间 |

> **为什么 `total_tokens` 建议不传**：让服务端算，避免两边口径不一致。你自己算的那个数如果和 `input + output` 对不上，统计页会看起来「总数不等于分项之和」。

> ⚠️ **`latency` 是毫秒，不是秒。** 很多 SDK 返回的是秒（float），直接塞进来会得到一条「0.0028 毫秒」的记录。转换写法见第 3 节。

> ⚠️ **`timestamp` 不带时区时，平台按 UTC 解释。**
> 北京时间 `2026-10-10 15:30`，要么发 `2026-10-10T15:30:00+08:00`（带时区），要么先转成 UTC 再发。**不带时区又直接发本地时间，记录会整体偏 8 小时**，而且在列表里看起来完全正常 —— 只是所有时间都不对。

**上报请求体里没有 `project_id`** —— 它由平台从 API Key 推导。这不是省事，是**安全性**：拿别人的 Key 也只能往那个 Key 所属的项目里写，越权在结构上就不可能发生。

### 2.3 响应

成功返回 **201**：

```json
{
  "id": 1024,
  "project_id": 13,
  "created_at": "2026-10-10T12:00:00.123456Z"
}
```

### 2.4 错误

| HTTP | 含义 | 你该怎么做 |
|---|---|---|
| **401** | Key 缺失 / 无效 / 已吊销 / 已过期 | 检查 `.env` 里的 Key 是否填对、是否被吊销了 |
| **422** | 字段不合法 | 响应体的 `detail` 里有具体字段和原因，照着改 |
| **5xx** | 平台自身故障 | 记本地日志，**丢弃这条**，不要让请求重试阻塞业务 |

> 401 的四种失败原因（缺 Key / Key 不存在 / Key 已吊销 / Key 已过期）**返回同一句话，不做区分**。这是有意的：区分了就等于给了攻击者一个「这把 Key 存不存在」的探测器。

> 401 的响应体里**不会回显你的 Key**。日志里可以放心打印响应内容；但请求头仍然不该打日志。

## 3. 完整示例（Python）

```python
"""AI Monitor 上报封装。后台线程发送，失败只记日志，绝不抛给业务。"""

import logging
import os
import threading
import time

import httpx

logger = logging.getLogger(__name__)

BASE_URL = os.getenv("AI_MONITOR_BASE_URL", "")
API_KEY = os.getenv("AI_MONITOR_API_KEY", "")
TIMEOUT_SECONDS = 3.0


def report(
    model: str,
    *,
    input_text: str | None,
    output_text: str | None,
    input_tokens: int,
    output_tokens: int,
    latency_ms: float,
    status: str,
    error: str | None = None,
    provider: str = "deepseek",
) -> None:
    """上报一次模型调用。没配环境变量就整个跳过，配了就发，失败也不影响调用方。"""
    if not (BASE_URL and API_KEY):
        return

    payload = {
        "provider": provider,
        "model": model,
        "latency": int(latency_ms),
        "status": status,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "input": input_text,
        "output": output_text,
    }
    if error:
        payload["error"] = error

    def _send() -> None:
        try:
            httpx.post(
                f"{BASE_URL}/api/v1/logs",
                json=payload,
                headers={"X-API-Key": API_KEY},
                timeout=TIMEOUT_SECONDS,
            )
        except Exception as exc:  # noqa: BLE001 —— 上报失败绝不能影响业务，这里必须全吞
            logger.warning("AI Monitor 上报失败(已忽略): %s", exc)

    threading.Thread(target=_send, daemon=True).start()
```

用法 —— 成功和失败**两条路都要报**：

```python
started = time.perf_counter()  # perf_counter 返回「秒」，所以下面要 * 1000
try:
    resp = client.chat.completions.create(model=MODEL, messages=...)
except Exception as exc:
    report(
        MODEL,
        input_text=prompt, output_text=None,
        input_tokens=0, output_tokens=0,
        latency_ms=(time.perf_counter() - started) * 1000,
        status="error", error=str(exc),
    )
    raise  # 业务自己的异常照常往上抛，与上报无关

report(
    MODEL,
    input_text=prompt,
    output_text=resp.choices[0].message.content,
    input_tokens=resp.usage.prompt_tokens,
    output_tokens=resp.usage.completion_tokens,
    latency_ms=(time.perf_counter() - started) * 1000,
    status="success",
)
```

> 注意 `except` 块里先 `report(...)` 再 `raise` —— **上报不改变业务的控制流**，该抛的异常照抛。这正是「不阻塞业务」在代码层面的样子。

环境变量留空时 `report()` 第一行就 return 了，**一条网络请求都不会发** —— 本地开发、跑测试时可以放心地不配。

## 4. 接完怎么验证（四条，都要过）

| # | 做什么 | 期望结果 |
|---|---|---|
| 1 | 上报一条，登录平台进该项目 → 「调用记录」页 | 最新一条就是刚上报的，时间、模型、耗时都对 |
| 2 | 看「预估费用」那一列 | 显示金额（**包括 `¥0.00`**）→ 模型名对上了；显示「—」 → 模型名没对上价格表 |
| 3 | **关掉平台，再跑一次你的 AI 项目** | **业务正常完成** ← 必测项 |
| 4 | 上报一条 `status="error"` 的 | 列表里是红色「失败」标签，点行打开抽屉能看到错误信息 |

> **第 3 条是必测项，不能跳。** 它验证的是「上报不阻塞业务」这条约束**真的落地了**，而不是靠祈祷。跳过它，等哪天平台挂了才发现你的 AI 项目也跟着挂了，那就白做了。

## 5. 常见问题

**Q：一次用户操作，平台上出现好几条记录？**

正常，多半是重试。如果你的 AI 项目对模型调用有重试（换个 prompt 重试、超时重试等），**每次重试都是一次真实的模型调用、一次真实的计费**，所以各报一条。

这是有意为之：失败和重试恰恰是异常分析最想看到的东西。判断标准是 —— **你在厂商账单上被扣了几次钱，平台上就该有几条记录**。

**Q：平台的成本和厂商账单对不上？**

三个已知原因，都不是 bug：

1. **缓存价差**。部分厂商（如 DeepSeek）对输入 token 分「缓存命中 / 未命中」两档价，平台的价格表只有一个 `input_price` 字段装不下两档，取的是**未命中价**。所以有缓存命中时，平台算出来的成本**偏高**。
2. **价格是写入时快照**。厂商调价后，**旧记录不会重算**。这是设计选择 —— 历史账单不该因为你改了一次价格就跟着变。改价格只影响之后的调用。
3. **Token 用量本身有偏差**。用量来自模型返回的 `usage` 字段，厂商自己也会漂。所以平台展示的一直叫「**预计**费用」。

**Q：能同时接入多个 AI 项目吗？**

能。**一个 AI 项目建一个平台项目、一把 Key。** 数据按 `project_id` 完全隔离，项目之间看不到彼此的数据 —— 这是平台的硬边界，不是靠前端过滤实现的。

**Q：平台在别的机器上，连不上怎么办？**

按这个顺序查：

1. 平台是否以 `--host 0.0.0.0` 启动的（uvicorn 默认只绑回环）
2. 防火墙是否放行了对应端口
3. 两边机器的网段是否互通（虚拟机要注意网络模式）

典型症状是**连接被拒绝 + 平台日志里一条请求都没有** —— 见到这个组合，基本可以直接断定是第 1 条。

**Q：上报的数据会不会拖慢我的接口？**

上报是「发出去就不管」的后台线程，主流程不等它。单条日志的写入耗时主要是 PostgreSQL 的一次 INSERT，不涉及任何重计算（成本是在写入时按快照算好的，不做 join）。

**Q：Key 泄露了怎么办？**

去项目的「设置」页吊销它，再新建一把。吊销是**立即生效**的。
